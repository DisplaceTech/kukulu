## F-01 — constraints and `extraVerify` are fixed for the whole flight

Logged by the planner (`stage: plan`, `category: static-constraints`, round
0, at `2026-10-06T15:32:36.767Z`):

> docs/foundry.json constraints and extraVerify are fixed for the whole
> flight. A rule the codebase only satisfies after task N (here
> py-no-gpl-import, fixed by P1-02) is violated from task 1, and an
> extraVerify script that a later task creates had to be wrapped in `test
> ! -f X || bash X`. A per-constraint "active from task ID" field, or
> tolerance for a missing script, would remove the reorder-and-annotate
> workaround.

## F-03 — the planner's own commit hung on a gpg pinentry

Logged by the planner (`stage: plan`, `category: signing`, round 0, at
`2026-10-06T05:03:31.180Z`):

> The plan commit failed at first because gpg signing timed out waiting
> for a gnome3 pinentry, which an unattended subagent cannot answer. I
> committed with -c commit.gpgsign=false. policies.signing "auto" only
> covers commits Foundry makes itself, so the plan stage has no documented
> fallback.

## F-04 — `foundry_review_submit` left a half-applied review when its signed commit failed

Logged by the reviewer (`stage: review`, `category: tool-refusal`, round 1,
at `2026-10-06T08:00:11.965Z`):

> foundry_review_submit wrote and staged REVIEW.md, PLAN.md (Review fixes
> round 1), PROGRESS.md and state.json (round 1, CHANGES REQUESTED), then
> its signed commit failed on a gpg pinentry timeout. That leaves the
> review half applied, and calling submit again could append the fix tasks
> twice. The tool could check that signing works before it mutates
> anything, or roll back on commit failure.
