# P3-13: the hook fast path and TARGET_MAX

Two SPEC §5.3 assumptions, measured and left unchanged.

## Hook fast path (budget 50 ms, ⚠️ ASSUMPTION)

Before: 50 ms, a test bound (`test/cleanroom.mjs`), no config key.
After: 50 ms. The measured overhead leaves at least 15 ms of headroom in the worst run.

Method: 30 runs of each hook script (`node scripts/cleanroom-guard.mjs`, `node scripts/cleanroom-log.mjs`) in a project with no policy, a `Read` payload on stdin, `CLAUDE_PROJECT_DIR` set; wall time with `process.hrtime.bigint()` around `spawnSync`. The overhead is each statistic minus the median of 30 runs of `node -e 0` on the same machine (median 31.8 ms, p90 39.0 ms, maximum 45.1 ms). For information, the same 30 runs with a policy present and a genesis in state, where the hook loads `mcp/cleanroom.mjs`, reads the project files and decides.

| Hook | Policy | Median | p90 | Maximum | Overhead at the median | Overhead at p90 | Overhead at the maximum |
|---|---|---|---|---|---|---|---|
| guard | none | 37.8 ms | 55.7 ms | 66.0 ms | 6.0 ms | 23.9 ms | 34.2 ms |
| logger | none | 34.1 ms | 44.9 ms | 46.8 ms | 2.3 ms | 13.1 ms | 15.0 ms |
| guard | present | 45.0 ms | 54.1 ms | 57.7 ms | 13.2 ms | not measured | not measured |
| logger | present | 43.6 ms | 47.5 ms | 54.3 ms | 11.8 ms | not measured | not measured |

The fast path stays inside the bound at every percentile: 6.0 ms at the median against 50 ms is 44 ms of headroom, and the worst single run (34.2 ms) leaves 15.8 ms. The spread is Node's own start-up noise. Even the full path, which does the real work, costs about 13 ms at the median.

## TARGET_MAX (4,000 characters, ⚠️ ASSUMPTION)

Before: 4,000. After: 4,000, with the evidence that follows.

Method: the `target` field of every entry in cleanflate's `provenance/tool-log.snapshot.jsonl` at commit `85f2100` (3,314 entries).

| Statistic | Value |
|---|---|
| Entries | 3,314 |
| Median | 93 characters |
| p95 | 2,058 characters |
| p99 | 4,000 characters |
| Maximum | 4,000 characters |
| Longer than 4,000 | 0 |
| Exactly 4,000 | 85 (2.6%), all `Bash` |

The snapshot cannot show a true maximum: cleanflate's own logger cut every Bash command at the same 4,000 characters, so 85 entries sit exactly on the cap and none is above it. Every other tool's target is far shorter (the next longest are the 500-character limits on MCP tool arguments). What the data does show is that a 4,000-character bound cuts about one entry in forty in a real flight, and only a long Bash command with an embedded script. A command that long is already recorded by its first 4,000 characters, which is where its destination and flags are.

## Decision

Neither value changes. A human may decide that 4,000 characters is too little for a recorded `Bash` command; the evidence for raising it is that 2.6% of cleanflate's commands reached the cap, and the evidence against is that a longer bound only makes the log larger.
