# P5-05: tuning cleanroom.idleGapHours

SPEC §6 F-02: `cleanroom.idleGapHours`, default 3, ⚠️ ASSUMPTION. A span longer than this between two consecutive log entries of one non-null stage is listed in an attestation bundle's `coverage.gaps` as an `idle` gap, so a reader can ask what happened while the log was quiet.

Before: 3 hours.
After: 3 hours, unchanged. In the only real log available, no same-stage gap is longer than 30.1 minutes, so every threshold from 31 minutes to many hours gives the same empty result there.

## Method

The data is cleanflate's `provenance/tool-log.snapshot.jsonl` at commit `85f210084a367dcc706c732f5776bf0563cdc0cd` (tag `v0.3.0-cleanroom`): 3,314 entries from 2026-09-29T14:42:53Z to 2026-10-01T02:34:02Z, one build with the stages plan (95), implement (1,740), review (392), fix (926), summarize (35) and no stage (126). Timestamps never go backwards. For every pair of consecutive entries with the same non-null stage, the gap is the difference of their `ts`, in hours: 3,164 gaps. This is the verifier's own definition of an idle gap, with the threshold taken away. The log was read in a throwaway script; nothing was written to the repository except this note.

| Statistic | Gap |
|---|---|
| median | 0.0014 h (5 s) |
| p90 | 0.012 h (43 s) |
| p95 | 0.028 h (1.7 min) |
| p99 | 0.160 h (9.6 min) |
| maximum | 0.502 h (30.1 min) |

| Threshold | Gaps over it |
|---|---|
| 15 minutes (0.25 h) | 3 |
| 1 hour | 0 |
| 3 hours | 0 |
| 6 hours | 0 |

The three gaps over 15 minutes are 30.1 minutes (2026-09-29T17:06:03Z to 17:36:10Z), 30.1 minutes (17:36:13Z to 18:06:20Z) and 17.3 minutes (2026-09-30T01:36:52Z to 01:54:10Z). cleanflate's own `provenance/SUMMARY.md` sums inter-call gaps under 15 minutes as active time and treats a longer gap as idle, which is a different question (how long was the session working) from the one the threshold answers (where might something have happened off the record).

## What this does and does not show

The build ran as one long flight, so the log has no overnight or multi-hour silence even though it spans two calendar days. That means 3 hours is not contradicted by the data: it would have listed nothing, and a 15 minute threshold would have listed three spans, each a long single tool call or a wait, none a sign of hidden work. It also means the data cannot say where a real hand-over to a person falls. A 3 hour threshold is about the length of one unattended stretch the pipeline treats as "still the same session", and a gap beyond it is long enough that a person could have edited the tree. One log is n = 1, so this is evidence about this flight and not a property of every flight.

## Decision

`cleanroom.idleGapHours` stays at 3. The first clean-room flight that has an overnight pause or a person stepping in is the measurement that can move it: if its bundle lists idle gaps that were only waits, raise it; if a hand edit slipped under it, lower it. The value is configurable per project in the meantime. This spike changes no code.
