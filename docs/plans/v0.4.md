# Foundry 0.4.0 — plan

Parallel workstreams. The `project-b` flight ran 26 tasks
one after another on one implementer, which took about 68 minutes of wall
clock. Many of those tasks had disjoint file sets: docs scaffold, test
spies, transport stubs, a CLI shim (F-05 in
[`../feedback/2026-09-23-project-b.md`](../feedback/2026-09-23-project-b.md)).

This release lets the planner split such tasks into **streams**. The
implement stage then runs each stream on its own implementer, in its own
git worktree, concurrently, and merges each stream back into the build
branch when it finishes.

This is a minor release, not a patch. It changes how a flight flows:
`go-flight` spawns more than one stage agent at once, `PLAN.md` gains a
field, and `foundry_next` gains a shape. That is the line 0.3.1 and
0.3.2 stayed behind.

Build this **after 0.3.2 has merged**. It depends on 0.3.2's
transcript-based guard (V3.2-01) and on `agentModel` (V3.2-02).

## How to work this plan

- **Git identity:** same rule as `v0.3.2.md`. Author and committer are
  both `Eric Mann <eric@eamann.com>`, and commits are signed. Check
  `git config user.email` before the first commit. Never
  `--no-gpg-sign`.
- Branch: `release/0.4.0` off `main` once 0.3.2 has merged. Make one
  commit per task, titled `<ID>: <title>`.
- `npm run check` before every commit, and `pre-commit run --all-files`
  before the PR.
- Use no dependencies.
- The new surface gets a new suite, `test/streams.mjs`, registered in
  `test/run.mjs`. Changes to existing tools extend their existing suites.
  The end-to-end flight goes in `test/drive.mjs`.
- Land documentation in the same commit as the behavior it describes.
- **Invariant you must not break:** every MCP tool handler is
  synchronous. `spawnSync`/`execFileSync` only, with no `await` in a
  tool path. The server therefore handles one tool call at a time,
  whichever stream's implementer sent it. That is what makes concurrent
  implementers safe with a single `PROGRESS.md` and a single
  `state.json`. Do not introduce async I/O anywhere in a tool handler. If
  a task seems to need it, stop and flag it.
- A plan with no `**Stream:**` fields must behave exactly as 0.3.2 did:
  byte-identical tool results, apart from new additive fields. Every
  existing suite passing unchanged is the proof.

## Decisions

- **Streams are declared per task in `PLAN.md`, and waves are derived,
  not declared.**
  - A task may carry `**Stream:** <slug>` (`/^[a-z][a-z0-9-]{0,23}$/`).
  - A **wave** is a maximal run of consecutive tasks, in `PROGRESS.md`
    order, that all carry a `Stream:`.
  - A task without one is **serial**, exactly as today, and acts as a
    barrier.
  - So the common shape "scaffold → parallel pieces → integration" is
    serial tasks, then a wave, then serial tasks, with no new syntax
    beyond one field.
  - Within a wave, tasks sharing a stream run in order on one
    implementer, and different streams run concurrently.
- **The partition is validated. An invalid one degrades to serial and is
  never halted on.** A wave is valid when all of the following hold:
  - no two streams in it name the same path in `**Files touched:**`
    (backticked tokens, compared after trimming, with a directory token
    such as `src/foo/` conflicting with any path under it);
  - no task depends on a task in a *different* stream of the same wave
    (depending on anything before the wave is fine);
  - it has at least two streams.

  An invalid wave runs serially, in `PROGRESS.md` order, as if it had no
  `Stream:` fields. Foundry auto-logs one feedback entry per wave
  (`stage: "plan"`, `category: "stream-partition"`) naming the
  conflict. A bad partition is a planning defect worth recording, but it
  never justifies stopping an unattended flight. `state.json` records
  the degraded waves (`serialWaves`) so the entry is logged once and the
  decision is stable across resumes.
- **The MCP owns the worktrees, not the harness.** `Agent`'s own
  `isolation: "worktree"` isn't available in every harness. It would
  also give each subagent a checkout the MCP server can't see: the
  server's `ROOT` is fixed at the session's project directory.
  - Instead, `foundry_run_start({ stream })` creates
    `.foundry/worktrees/<stream>` on branch `<build-branch>--<stream>`,
    cut from the build branch's current HEAD.
  - Stream-scoped tool calls run git and verify commands in that
    worktree.
  - The worktree lives *inside* the project directory, so the
    implementer's existing `acceptEdits` permission covers it.
  - `run_start` adds `.foundry/worktrees/` to `.gitignore` in the commit
    it already makes, next to `implement.lock`.
- **`PROGRESS.md`, `PLAN.md` and `state.json` live only in the main
  checkout.**
  - Stream-scoped `task_next`/`task_done`/`task_block` read and write
    them in `ROOT` and commit them on the build branch.
  - Task *code* commits happen in the stream worktree, on the stream
    branch.
  - Stream implementers never edit `docs/PROGRESS.md`, `docs/HANDOFF.md`
    or anything under `.foundry/`. Their worktree copies are stale by
    design.
  - Because the stream branches never touch those files, merging a
    stream back cannot conflict on bookkeeping.
- **Each stream is merged when it finishes, not at the end of the
  wave.**
  - `foundry_stream_finish({ stream })` requires no open tasks in that
    stream and a clean worktree.
  - It then runs `git merge --no-ff <stream-branch>` on the build branch
    in `ROOT`, with the message `merge stream <stream> (wave <n>)`.
    Nobody else works in `ROOT` during a wave, and the server is
    serialized.
  - It then removes the worktree and deletes the stream branch.
  - On a merge conflict (which the partition check makes unlikely, not
    impossible), it runs `git merge --abort`, keeps the stream branch
    and worktree, and sets `st.halted` with a reason naming both.
    Foundry auto-logs `category: "stream-merge"`. A human resolves it.
    This is the one stream failure that halts, because Foundry can't
    guess a merge.
- **Verification is serialized.** `runShell` is `spawnSync`, and the
  server handles one call at a time, so two streams' verify runs never
  overlap. This is deliberate for 0.4.0: suites often share ports,
  containers or databases (wp-env is the motivating case). Most of a
  stream's wall clock is model time, not test time, so the speedup
  mostly survives. Concurrent verification is out of scope.
- **`parallel.maxStreams` in `docs/foundry.json`** (a positive integer,
  default `3`).
  - `1` disables parallelism: every wave runs serially, and nothing is
    logged, because that is the operator's choice.
  - When a wave has more streams than the cap, `foundry_next` hands out
    the first `maxStreams` streams in order. The rest go out on the
    next `foundry_next` after those finish.
- **The controller spawns a wave's streams concurrently and waits for
  all of them.**
  - `foundry_next` at a wave returns `stage: "implement"` with a
    `streams` array: `[{ stream, agent, agentFallback, agentModel,
    prompt }]`.
  - `go-flight` spawns every entry in one message (parallel `Agent`
    calls), waits until every one has finished, then calls
    `foundry_next` again.
  - The "exactly one stage at a time" rule becomes "exactly one
    `foundry_next` result at a time". A wave's streams are one result.
  - If a stream's implementer stops with that stream's tasks still open,
    the next `foundry_next` simply hands that stream out again.
    `run_start({ stream })` is idempotent and resumes the existing
    worktree. The controller never has to reason about it.
- **The guard learns streams, and still never guesses block.**
  - On a `SubagentStop` for the implementer, the hook reads the
    subagent's transcript (`agent_transcript_path`, else
    `transcript_path`, sidechain entries included) for the *last*
    `foundry_run_start` `tool_use`, and takes its `input.stream`.
  - With a stream, it blocks only if that stream has open tasks. With no
    stream, it uses the serial rule as today.
  - If the stream can't be determined, it allows.
  - The controller's re-hand-out is the backstop. The guard is an
    optimization, not the only safety net.
  - The hook needs a task→stream map without parsing `PLAN.md`, so
    `PROGRESS.md` task lines carry the stream as a suffix tag:
    `- [ ] P2-03 Title {stream: api}`.
- **Review-fix rounds stay serial in 0.4.0.** The reviewer does not
  assign streams, and `R*-*` tasks have no `Stream:`. Parallel fix
  rounds are a possible later release.
- **HANDOFF.md is still written once, by a serial implementer.** When a
  plan ends with a wave, the post-wave `foundry_next` sees the lock with
  no open tasks, and returns the existing "finish the handoff" implement
  stage. Stream implementers put their interpretation choices in their
  task logs. The handoff writer reads those logs.

## V4-01: stream fields, waves, and partition validation (read-only)

**Goal:** Foundry can parse streams and waves and judge a partition,
without any change to how a run executes.

**Files touched:** `mcp/server.mjs`:

- `planTask` gains `stream`;
- `TASK_LINE` accepts an optional trailing `{stream: <slug>}`, and
  `parseProgress` records it;
- new `waves(pr)` and `validateWave(wave)`;
- `cfg()` gains `parallel.maxStreams` with validation;
- `status()` gains `waves`.

Also `test/streams.mjs` (new), `test/run.mjs`, `docs/mcp-tools.md`
(`foundry_status` table) and `docs/operations.md` (config table).

**Design constraints:**

- `planTask` reads `**Stream:**` like `**Depends on:**`. It is absent,
  empty or `none` for a serial task.
- `waves(pr)` returns
  `[{ index, taskIds, streams: { <slug>: [ids…] }, valid, reason }]`, in
  order, using the stream tag on `PROGRESS.md` lines, which is
  authoritative at run time.
- `validateWave` implements the three rules in Decisions. `reason` names
  the offending tasks and the shared path or the cross-stream
  dependency.
- `maxStreams` must be a positive integer. Anything else refuses, the
  same way a bad `policies` value does. An unknown key under `parallel`
  also refuses.
- `status().waves` gives each wave's index, stream names, per-stream
  open counts, `valid` and `reason`. It is `[]` for a plan with no
  streams.

**Acceptance tests** (`test/streams.mjs`):

- A plan of serial ×2, a wave of streams `a`/`b`, then serial ×1 yields
  one wave with the right ids per stream.
- Two separated runs of streamed tasks yield two waves.
- A path shared across streams makes the wave invalid, and the reason
  names both tasks and the path. A directory token that prefixes the
  other stream's file is caught too.
- A cross-stream dependency inside the wave makes it invalid.
- A dependency on a pre-wave serial task is fine.
- A single-stream wave is invalid, with reason "only one stream".
- `{stream: x}` on a `PROGRESS.md` line round-trips through
  `parseProgress`/`writeProgress` unchanged.
- `parallel.maxStreams: 0`, `"3"`, and `parallel.foo` each refuse.
- Every pre-existing suite passes unchanged.

**Verification:** `npm test`.

**Depends on:** none.

## V4-02: stream-scoped run_start, task_next, task_done, task_block, verify

**Goal:** One implementer can run one stream end to end in its own
worktree, while the bookkeeping stays in the main checkout.

**Files touched:** `mcp/server.mjs`:

- `git(args, { cwd })`, defaulting to `ROOT`;
- `runShell(cmd, timeoutMs, cwd)`;
- `streamDir(stream)`;
- `runStart`, `taskNext`, `taskDone`, `taskBlock` and `verify` accept an
  optional `stream`;
- input schemas.

Also `test/streams.mjs` and `docs/mcp-tools.md`.

**Design constraints:**

- `runStart({ stream })`:
  - First do the ordinary (non-stream) start if the run isn't started
    yet (branch, lock, `.gitignore` gaining `.foundry/worktrees/`).
  - Then, if `.foundry/worktrees/<stream>` doesn't exist, create it:
    `git worktree add -b <build>--<stream> .foundry/worktrees/<stream> HEAD`.
  - Refuse if `stream` isn't in the *current* wave. The current wave is
    the first wave with open tasks, and only when no serial task before
    it is still open.
  - Return `{ stream, cwd: <absolute worktree path>, branch, … }`.
  - Idempotent: calling it again returns the same `cwd` and resets the
    guard counter.
- `taskNext({ stream })`: considers only that stream's tasks in the
  current wave, and applies the same dependency-skip rule. Without
  `stream`, it refuses if the next open task belongs to a *valid* wave.
  The error says to use the streams `foundry_next` returned.
  - A wave recorded in `st.serialWaves`, or one where
    `maxStreams === 1`, is handed out serially: its tasks are treated as
    serial.
- `taskDone({ stream, id, log })`:
  - Check the HEAD subject and a clean tree *in the worktree*.
  - Record the task's sha from the worktree.
  - Update and commit `PROGRESS.md` in `ROOT` on the build branch.
- `taskBlock({ stream, … })`: reset and clean *the worktree*, and leave
  `ROOT` alone.
- `verify({ files, stream })`: runs commands with `cwd` set to the
  worktree. Constraints scan the worktree's tracked files.
- Every `stream` argument must name an existing stream of the current
  wave. Anything else refuses with the list of legal streams.

**Acceptance tests** (`test/streams.mjs`, real git repos through
`harness.mjs`):

- `run_start({stream:"a"})` on a fresh plan starts the run, creates the
  worktree and branch, and returns an absolute `cwd`. Calling it again
  is idempotent.
- `task_next({stream:"a"})` never returns a `b` task.
- A commit in the `a` worktree followed by `task_done` marks the task
  `[x]` in `ROOT`'s `PROGRESS.md`, and the progress commit is on the
  build branch, not the stream branch.
- Interleaved calls for `a` and `b` (a, b, a, b) leave `PROGRESS.md`
  consistent, with every done task logged once.
- `task_block` in stream `a` discards the worktree's uncommitted changes
  and doesn't touch an untracked file in `ROOT`.
- `verify({stream:"a"})` runs in the worktree. Prove it with a verify
  command that writes `$PWD` to a file.
- Serial `task_next` refuses while a valid wave is current, and serves
  the wave's tasks serially once the wave is in `serialWaves`.

**Verification:** `npm test -- streams implement`.

**Depends on:** V4-01.

## V4-03: `foundry_stream_finish` — merge back, clean up

**Goal:** A finished stream lands on the build branch, and its worktree
disappears.

**Files touched:** `mcp/server.mjs` (`streamFinish`, a `TOOLS` entry,
and `runFinish` refusing while any stream worktree exists),
`agents/implementer.md` (`tools:`), `test/streams.mjs`,
`docs/mcp-tools.md`, `docs/architecture.md` (stage machine and "State on
disk": worktrees and stream branches).

**Design constraints:**

- It refuses when:
  - the stream has open tasks (the error names them);
  - the worktree is dirty.
- Merge sequence:
  1. In `ROOT`, check that the build branch is checked out and the
     tracked tree is clean.
  2. `git merge --no-ff -m "merge stream <s> (wave <n>)" <build>--<s>`.
  3. `git worktree remove .foundry/worktrees/<s>`.
  4. `git branch -d <build>--<s>`.
- A stream whose tasks are all blocked or skipped still merges (probably
  a no-op merge) and cleans up. Blocked tasks go to review like any
  others.
- On conflict:
  - `git merge --abort`, and keep the stream branch and the worktree;
  - set `st.halted` to a reason naming the stream, the conflicting
    paths, and the manual steps;
  - auto-log `stream-merge` feedback, and commit `state.json` and the
    feedback file together;
  - return `{ merged: false, halted }`.
- Return
  `{ stream, merged: true, mergeCommit, remainingStreams: [...] }`.
- `runFinish` refuses while `.foundry/worktrees/*` exists. The error
  names each stream and says to call `foundry_stream_finish`.
- The tool count becomes sixteen. Update the `plugin` suite assertion.
  The prose counts wait for V4-08.

**Acceptance tests:**

- Two streams touching disjoint files each finish and merge. The build
  branch contains both sets of task commits and two merge commits. No
  worktrees or stream branches remain.
- A forced conflict (both streams edit the same file, bypassing
  validation by hand-editing `PROGRESS.md`): the second finish aborts
  cleanly, `st.halted` is set, `foundry_next` returns `halt`, and one
  `stream-merge` feedback entry exists.
- A finish with open tasks refuses. A finish with a dirty worktree
  refuses.
- `run_finish` with a leftover worktree refuses.

**Verification:** `npm test -- streams`.

**Depends on:** V4-02.

## V4-04: `foundry_next` hands out waves; go-flight and implement learn streams

**Goal:** An unattended flight actually runs a wave concurrently.

**Files touched:** `mcp/server.mjs` (`next()`, `PROMPTS.implement` with
a stream variant, the `serialWaves` state field, auto-logging an invalid
partition), `skills/go-flight/SKILL.md`, `skills/implement/SKILL.md`,
`test/state.mjs`, `test/streams.mjs`, `test/plugin.mjs`,
`docs/architecture.md` (the stage machine, and a concurrency section
stating the synchronous-handler invariant), `docs/mcp-tools.md`.

**Design constraints:**

- When the current wave is valid and `maxStreams > 1`, `next()` returns
  the ordinary implement result (for backward-compatible fields), plus
  `streams`:
  - streams with open tasks only, the first `maxStreams` of them;
  - each one gets its own `prompt` and the same `agent`/`agentModel`
    fields.
- When the current wave is invalid and not yet in `st.serialWaves`:
  - add it to `serialWaves`;
  - auto-log `stream-partition` feedback (`stage: "plan"`, the reason
    verbatim);
  - commit `state.json` and the feedback file together as
    `chore: wave <n> runs serially`;
  - then return an ordinary serial implement result. `next()` is
    otherwise read-only. This one write is justified because the
    decision must be stable and recorded, and it is the same shape as
    the 0.3.1 auto-log points.
- Stream prompt: "Run the Foundry implement stage for stream `<s>` of
  wave `<n>`. Call `foundry_run_start` with `stream: "<s>"`, and work
  only inside the `cwd` it returns. Loop `foundry_task_next({stream})`
  until done, then call `foundry_stream_finish({stream})`. Do not write
  `docs/HANDOFF.md` and do not call `foundry_run_finish`." Follow it
  with the policy sentence.
- `go-flight`, loop step 4: when `streams` is present and non-empty,
  spawn one `Agent` per entry *in a single message*, so they run
  concurrently. Then wait until every one of them has finished (returned
  or notified) before step 1. Amend the "exactly one stage at a time"
  paragraph to match. Keep the existing rules: no polling, no
  re-spawning a slow stream, no interpreting reports.
- `implement` skill: add a "Stream mode" section:
  - When `foundry_run_start` returns a `cwd`, every Read, Write and Edit
    uses absolute paths under it.
  - Every Bash command starts with `cd <cwd> &&`.
  - Never touch `docs/PROGRESS.md`, `docs/HANDOFF.md` or `.foundry/`.
  - Put interpretation choices in the task log, since there is no
    handoff to hold them.
  - Finish with `foundry_stream_finish`.
  - A `stream` argument goes on every `task_*` and `verify` call.

**Acceptance tests:**

- `test/state.mjs`:
  - at a valid two-stream wave, `foundry_next` returns `streams` of
    length 2 with distinct prompts naming each stream;
  - with `maxStreams: 1`, it returns no `streams` and nothing is logged;
  - with three streams and `maxStreams: 2`, the result has two streams,
    and after those finish, the next result has the third.
- `test/streams.mjs`: an invalid wave produces exactly one
  `stream-partition` entry and one `chore: wave <n> runs serially`
  commit, even across three `foundry_next` calls. After that, the wave's
  tasks are served serially.
- `test/plugin.mjs`:
  - go-flight mentions spawning `streams` in a single message and
    waiting for all;
  - the implement skill has a "Stream mode" section naming
    `foundry_stream_finish`;
  - the implementer agent's `tools:` includes `foundry_stream_finish`.

**Verification:** `npm test -- state streams plugin`.

**Depends on:** V4-03.

## V4-05: the implement guard is stream-aware

**Goal:** A stream implementer that stops with its own stream still
open is pushed back into its loop. One whose stream is done is not held
hostage by another stream's open tasks.

**Files touched:** `scripts/implement-guard.mjs`, `test/guard.mjs`.

**Design constraints:**

- For a `SubagentStop`, find the last `foundry_run_start` `tool_use` in
  the subagent's transcript (the V3.2-01 parser, sidechain included) and
  read `input.stream`.
- With a stream, count open tasks tagged `{stream: <s>}`. Block only if
  that count is above zero, and name the stream in the reason.
- With no stream, apply the existing rule.
- An unreadable transcript, or a missing `tool_use`, means allow.
- The re-block counter stays one shared counter in the lock. It resets
  on every task state change, from any stream, which is correct: work
  moving anywhere proves the flight isn't wedged.

**Acceptance tests:**

- Stream `a` with open tasks and a transcript whose `run_start` input is
  `{stream:"a"}`: block, and the reason names `a`.
- Stream `a` done, `b` open, and the transcript says `a`: allow.
- A transcript with two `run_start` calls (`a`, then `b`): uses `b`.
- A stream-less `run_start` gets the serial behavior, unchanged.

**Verification:** `npm test -- guard`.

**Depends on:** V4-04.

## V4-06: the planner carves streams

**Goal:** Plans actually use streams where they help, and only where
they are safe.

**Files touched:** `skills/plan-build/SKILL.md` (format and rules),
`agents/planner.md` if its body restates the format, `templates/` if a
plan template exists, `test/plugin.mjs`, `docs/writing-specs.md` (a
short note that SPECs listing independent components parallelize
better).

**Design constraints (the rules the skill states):**

- Add `**Stream:**` to the task format block. It is optional, and a
  lowercase slug.
- Put tasks in a stream only when they can be built without seeing each
  other's code. **Files touched** must be concrete backticked paths, and
  they must be disjoint across the streams of a wave.
- Shared-edit hotspots never go inside a wave. Put their edits in a
  serial task after the wave. Hotspots include:
  - package manifests and lockfiles;
  - a test runner's registry;
  - a changelog or a docs index;
  - DI or container registration;
  - routes tables.
- A wave is consecutive streamed tasks. Streams in a wave depend only on
  tasks *before* the wave, or on earlier tasks in their own stream.
- Keep to at most `parallel.maxStreams` streams per wave (read it from
  `docs/foundry.json` if the planner writes one, default 3), and at
  least two.
- Phase-end tasks (the `implement` skill's existing concept) are always
  serial.
- `PROGRESS.md` format: a streamed task's line ends in `{stream: <s>}`.
- If a plan would have streams but they don't make sense for this
  project, don't force them. A fully serial plan is still correct.

**Acceptance tests** (`test/plugin.mjs`): `plan-build` documents
`**Stream:**`, the `{stream: …}` PROGRESS suffix, the disjoint-files
rule, and the hotspots rule.

**Verification:** `npm test -- plugin`. Read the skill top to bottom as
the planner would.

**Depends on:** V4-01.

**Design constraints:** Extend the existing drive harness. Simulate each
