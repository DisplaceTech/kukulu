# Foundry 0.3 — plan

Derived from `FEEDBACK.md` (the project-a flight, 2026-09-20/21, plugin
0.2.0) on 2026-09-21. Every F-item in that file is addressed here, plus a
polish pass so the next engineer who installs Foundry on their own project
does not need to have read that flight's transcript.

This is a plan for an implementing agent (Sonnet) working on a branch, with a
single PR at the end for the owner to review. It is written in the same shape
the Foundry's own planner uses: ordered tasks with goals, files, tests,
out-of-scope, verification and dependencies. Task text is meant to be
self-sufficient; when in doubt, `FEEDBACK.md` is the primary source and the
current code is the second.

## How to work this plan

- Branch: `release/0.3` off `main`. One commit per task, titled
  `<ID>: <title>`, body explaining *why* (the F-item it closes). Conventional
  prefixes (`feat(mcp):`, `fix(guard):`, `docs:`, `test:`, `chore:`) are fine
  after the ID, e.g. `V3-04: fix(guard): count stalls, not stops`.
- Run `npm run check` before every commit. `pre-commit run --all-files`
  before the PR. Both must be clean; CI runs the same set on Node 22/24/26,
  macOS and with `gh` removed.
- No dependencies. Not in the server, not in the tests, not in the scripts.
  The MCP server speaks raw JSON-RPC over stdio on purpose.
- Tests live with the behaviour: extend the suite that owns the tool
  (`test/implement.mjs` for run_start/task_*/run_finish, `test/review.mjs`
  for review_submit/summary_commit, `test/state.mjs` for status/next,
  `test/routing.mjs` for agents_sync/config_show, `test/guard.mjs` for the
  hook, `test/plugin.mjs` for manifests/frontmatter/docs, `test/drive.mjs`
  for the end-to-end flight). Add a new suite only for a genuinely new
  surface (V3-12 adds one).
- Every behaviour change lands with its documentation in the same commit:
  `docs/mcp-tools.md` for tool contracts, `docs/operations.md` for
  runbook/config, `docs/architecture.md` for invariants, `README.md` where
  the quickstart or per-project section is affected, and the relevant
  `skills/*/SKILL.md` for anything a stage agent must do differently.
- Error messages are written for a model that has to recover from them: say
  what is wrong and what to do instead.
- Do not touch `FEEDBACK.md` until V3-15 says to. Do not rename existing
  tools. Do not change the `PROGRESS.md`/`PLAN.md` formats the MCP parses.
- If a task turns out to be impossible as written, do not work around it:
  leave a note in the PR description under "Deviations" and move on.
- The PR description lists, per F-item, the task that closed it and how.

## Decisions

Decisions taken here so the implementer does not have to relitigate them.

- **F-01 → allow model invocation of `go-flight`.** The controller makes no
  engineering decisions and only calls three read-only tools plus `Agent`,
  so the risk the flag guarded against is nil. The literal slash command
  stays the documented entry point.
- **F-02/F-06 → fall back, do not stop.** When a generated agent is not
  loadable, the controller spawns the plugin's own `foundry:<role>` agent
  with the resolved model passed as the `Agent` tool's `model` override.
  Effort is lost in that case (the `Agent` tool has no `effort` parameter),
  which is acceptable for one flight. The `RESTART REQUIRED` stop survives
  only for models the `Agent` tool cannot name (anything routed through
  claude-code-router), because there the fallback would silently run the
  wrong model. `foundry_next` decides which case applies; the controller
  does not reason about it.
- **F-03 → `foundry_agents_sync` writes the allow rule** into the project's
  `.claude/settings.local.json` (never the committed `settings.json`, never
  the user's global file), merging with whatever is there, and reports what
  it did. The user can still choose to put the rule elsewhere; the sync
  treats an existing matching rule in either project file as "present".
- **F-07 → the guard blocks only the agent that armed the run.** See V3-03
  for the mechanism. The controller session is never blocked.
- **F-08 → the cap counts stalls.** `foundry_task_done`, `foundry_task_block`
  and `foundry_run_start` reset the counter, so the cap bounds re-blocks
  *per task*, not per run. The default drops from 500 to 60: at the observed
  ~6 blocked stops per healthy task, 60 is ten tasks' worth of blocking with
  no progress, which is a wedge by any definition.
- **F-05 → run policies live in `docs/foundry.json`** under a `policies`
  block (`signing`, `push`, `pr`), are recorded in `.foundry/state.json` at
  `run_start`, are forwarded to every stage in the prompt `foundry_next`
  builds, and are honoured by the MCP where the MCP does the work (push, PR)
  and by the skill where the model does (commit signing failures mid-run).
  A run that cannot proceed for an operator-level reason gets a new tool,
  `foundry_run_halt`, that stops the flight without discarding work.
- **F-09/F-17 → pre-existing untracked files are invisible to the run.**
  `run_start` records them; `task_done` and `run_finish` ignore them;
  `task_block`'s `git clean` spares them (today it would *delete* them,
  which is worse than F-09); the implement skill forbids touching them; the
  review skill treats an unexplained `.gitignore` edit as a finding.
- **F-10/F-11 → the MCP owns the review round number.** `foundry_status`
  and `foundry_next` expose `reviewRound` (the number `review_submit` will
  stamp), the review prompt states it, and `review_submit` refuses a
  `REVIEW.md` whose `Round:` line disagrees. Fix-task ids are still assigned
  by the MCP.
- **F-13/F-15 → converging rounds do not count against the cap.**
  `maxRounds` (default 3) now bounds *non-converging* rounds: a round whose
  fix-task count is not smaller than the previous round's. A separate
  `maxRoundsHard` (default 6) is the absolute ceiling. Advisory findings that
  need no task go in a `## Notes` section of `REVIEW.md` and do not force a
  round. The per-round auto-approve threshold suggested in F-13(c) is
  rejected: approving with open findings hides work from the summary.
- **F-14 → constraints become data with fixtures, checked by the MCP.**
  `docs/foundry.json` gains `constraints`, `foundry_verify` self-tests each
  rule against its fixtures before scanning, and the planner/reviewer
  skills require every mechanically checkable `CLAUDE.md` constraint to be
  expressed there. A grep with a blind spot fails its own fixture instead of
  passing silently for three rounds.
- **F-16 → stage agents declare their tools explicitly and the summarize
  skill tells the agent to write via shell if `Write` is refused.** The
  refusal came from the harness, not from Foundry, so the fix is to make the
  intended tool set explicit and to spend no turns on the refusal.
- **F-18 → every bookkeeping commit that follows a push is pushed.**
  `review_submit` and `summary_commit` push when there is an origin and the
  push policy allows; `run_start` pushes the base branch before branching
  from it so a PR's diff is the build, not the plan.
- **F-12 → published as calibration data**, not code: `docs/operations.md`
  gets the observed per-stage numbers, and `verify` commands can carry their
  own timeout.
- **Compound step.** The summarizer gains a "Pipeline friction" section so
  the next flight's feedback is collected by the pipeline itself, and this
  flight's `FEEDBACK.md` is preserved under `docs/feedback/` as the first
  entry.

## Conventions

- Task ids are `V3-<nn>`. Commit title `V3-<nn>: <title>`.
- "Refuses when" in a task means a `ToolError` with a message that names the
  fix, and a test in the owning suite asserting the message.
- "Documented in" means the named file is updated in the same commit.
- Where a task says "state" it means `.foundry/state.json` via
  `loadState`/`saveState`; new keys get a default in `DEFAULT_STATE` so a
  0.2 state file still loads.
- Where a task says "config" it means `docs/foundry.json` via `cfg()`; new
  keys get a default there and a row in the config table in
  `docs/operations.md`.

## Phase A — controller and guard (the flight can run unattended)

### V3-01: go-flight is model-invocable and event-driven

**Goal:** A user can say "run the foundry flight" and the controller loop is described the way the harness actually behaves.
**Files touched:** `skills/go-flight/SKILL.md`, `test/plugin.mjs`, `README.md` (Quickstart, Per-project use), `docs/operations.md` (Running a flight), `CHANGELOG.md`
**Design constraints:**

- Remove `disable-model-invocation: true` from the frontmatter. Keep `model: sonnet`, `effort: low`. Add every new tool from this plan to `allowed-tools` in both the `mcp__plugin_foundry_foundry__` and `mcp__foundry__` forms as later tasks introduce them (V3-07 adds `foundry_run_halt`; nothing else is controller-facing).
- Rewrite the loop section so it is correct under both harness behaviours the docs allow: an `Agent` call either blocks until the stage finishes or returns at once and delivers a completion notification later. Phrase the loop as "when the stage has finished (the call returned, or the notification arrived), call `foundry_next` again". Say explicitly: do not poll `foundry_status` while a stage is running, do not sleep, do not spawn a second stage while one is running, do not re-spawn a stage because a notification is slow, and never interpret the stage's report.
- State that the `Agent` tool takes `model` but not `effort`; effort only ever comes from the agent file. The controller never tries to set it.
- Pass `model` from `foundry_next` to the `Agent` tool whenever `foundry_next` returns `agentFallback: true` (V3-02). When it is `false`, pass only `subagent_type` so the generated agent's own `model`/`effort` apply.
- Keep the "never AskUserQuestion" rule, the stop block, and the no-merge rule.
- `test/plugin.mjs` currently asserts the go-flight frontmatter; update the assertions to the new contract (no `disable-model-invocation`, allowed-tools covers every controller-facing tool in both forms).

**Acceptance tests:** `test/plugin.mjs`: go-flight has no `disable-model-invocation` key; its `allowed-tools` names `foundry_status`, `foundry_next`, `foundry_agents_sync` and `foundry_run_halt` in both prefixed forms; the body contains the words "notification" and "do not poll".
**Out of scope:** the fallback decision itself (V3-02); any change to the stage skills.
**Verification:** `npm test -- plugin`; read the rewritten SKILL.md top to bottom as if you were the controller and confirm no step requires blocking.
**Depends on:** none

### V3-02: `foundry_next` decides between generated agent, plugin fallback, and restart

**Goal:** The first flight in a project runs to completion without a restart whenever the resolved model is one the `Agent` tool can name.
**Files touched:** `mcp/server.mjs` (`next`, `agentsSync`, `status`), `skills/go-flight/SKILL.md`, `test/state.mjs`, `test/routing.mjs`, `test/drive.mjs`, `docs/mcp-tools.md` (`foundry_next`, `foundry_agents_sync`), `docs/routing.md`, `docs/operations.md` (symptom table), `README.md` (Per-project use), `CHANGELOG.md`
**Design constraints:**

- `foundry_next` gains three fields: `agentFallback` (boolean), `fallbackAgent` (the `foundry:<role>` name, always present for stage results), and `restartRequired` (boolean). The stage machine and prompts do not change.
- Claude Code hot-reloads project agent files within seconds of a change, with one documented exception: the first agent file created in a new `.claude/agents` directory is not picked up until the session restarts (sub-agents reference, "hot reload"). So `agentFallback` is true when the generated file for the role is absent, **or** when this server process's `agentsSync` call created the `.claude/agents` directory itself (track it in module state: `let agentsDirCreatedThisProcess = false`, set in `agentsSync` when `fs.existsSync(P.agentsDir)` was false before the `mkdirSync`). A routing *change* in an existing directory hot-reloads and needs no fallback. The MCP server process lives as long as the session, so process state is the right proxy for "since this session started". Keep the `agentsGeneratedThisSession` list in `foundry_status` (roles written this process) as diagnostic information only.
- When `agentFallback` is true and the resolved model is not an Anthropic alias (`isAnthropicModel` false), set `restartRequired: true` and `agent: null`, and put the reason in `reason`. Otherwise `agent` is the generated name when it exists on disk (the harness may hot-load it, per F-06) and `fallbackAgent` is what to use if that spawn fails with "not found".
- `foundry_agents_sync` keeps `changed`, but the controller no longer stops on it. Add `restartRequired` to its result using the same rule (any changed role whose model is non-Anthropic) so a headless launcher can still detect the one case that needs a relaunch.
- go-flight: on `restartRequired: true` print the existing `FOUNDRY: RESTART REQUIRED` line and stop. Otherwise spawn `agent`; if the spawn fails with an agent-not-found error, spawn `fallbackAgent` with `model` and continue. Only print `RESTART REQUIRED` if the fallback also fails.
- `foundry_status` gains `agentsGeneratedThisSession` (the set above) so a human can see why fallback is in effect.

**Acceptance tests:** `test/state.mjs`: `next` on a repo with no generated agents returns `agentFallback: true`, `fallbackAgent: "foundry:planner"`, `restartRequired: false`; after `agents_sync` in the same server process it still returns `agentFallback: true` but `agent: "foundry-planner"`; with `docs/foundry.json` routing the planner to `Ollama/x` and no file on disk, `restartRequired: true` and `agent: null`. `test/routing.mjs`: `agents_sync` reports `restartRequired` correctly for Anthropic and non-Anthropic models. `test/drive.mjs`: a fresh server process against an already-synced repo reports `agentFallback: false`.
**Out of scope:** effort in the fallback path (the Agent tool has no such parameter; document the loss in `docs/routing.md`).
**Verification:** `npm test -- state routing drive`.
**Depends on:** V3-01

### V3-03: the guard blocks only the agent that armed the run

**Goal:** A controller session waiting on a background implementer is never blocked by the implement guard, and never burns its counter.
**Files touched:** `hooks/hooks.json`, `scripts/implement-guard.mjs` (replaces `implement-guard.sh`), `scripts/lint.sh`, `mcp/server.mjs` (`runStart`, `status`), `test/guard.mjs`, `test/plugin.mjs`, `test/harness.mjs` (`GUARD` path), `test/implement.mjs`, `docs/architecture.md` (The unattended contract, State on disk), `docs/operations.md`, `README.md` (The guard hook), `CONTRIBUTING.md` (lint description), `CHANGELOG.md`
**Design constraints:**

- Two layers, both from the Claude Code hooks reference (<https://code.claude.com/docs/en/hooks>): the `SubagentStop` hook entry in `hooks.json` gets a `matcher` on `agent_type` — `^(foundry:implementer|foundry-implementer)$` — so the harness never even runs the guard for a reviewer, planner, summarizer or any unrelated subagent. The `Stop` entry stays unmatched (Stop has no agent to match), and the script decides.
- The hook reads its JSON input from stdin (today it reads nothing). The JSON handling is now the whole job, so rewrite it as `scripts/implement-guard.mjs` (`#!/usr/bin/env node`; the plugin already requires Node ≥ 22). Update `hooks.json`, `test/harness.mjs`, `test/guard.mjs`, `scripts/lint.sh` (node --check instead of bash -n for this file) and CONTRIBUTING. Keep the exit-0-with-no-output contract for "allow".
- Documented input fields to rely on: `hook_event_name`, `transcript_path`, `cwd`, and for `SubagentStop` also `agent_id` and `agent_type`. Do not use `last_assistant_message`.
- Decision rule, in order:
  1. No lock, or no open tasks: allow (unchanged).
  2. `hook_event_name` is `SubagentStop`: block if `agent_type` is `foundry:implementer` or `foundry-implementer` (belt and braces with the matcher; a project `.mcp.json` install of the server or a hand-edited hooks file may not carry the matcher). Any other `agent_type`: allow. Missing `agent_type`: fall back to the transcript check below.
  3. `hook_event_name` is `Stop`: block only if this session's transcript (`transcript_path`) contains the string `foundry_run_start`, i.e. the implement stage is being run directly in the main session (`/foundry:implement` by hand, or `claude -p`). A controller session never calls `run_start`, so it is never blocked and never touches the counter.
  4. Any other event, unreadable or empty input, or an unreadable transcript: allow, and write nothing.
- Only increment the counter when actually blocking.
- `foundry_run_start` writes the lock as JSON from now on: `{ "count": 0, "armedAt": "<iso>", "round": N }`. The hook must accept both the legacy bare-number form and the JSON form (a 0.2 run may be resumed by 0.3), and must preserve unknown keys when it rewrites the count. `foundry_status` gains `lockCounter` (number or null).
- Keep `CLAUDE_PROJECT_DIR` as the project root with `cwd` from the input as the fallback and `process.cwd()` last.

**Acceptance tests:** `test/guard.mjs` (rewritten to feed stdin JSON and a fake transcript file): a `Stop` with a transcript lacking `foundry_run_start` is allowed and does not increment; a `Stop` whose transcript contains it is blocked; a `SubagentStop` with `agent_type: "foundry-implementer"` is blocked, with `foundry:implementer` is blocked, with `Explore` is allowed; a `SubagentStop` without `agent_type` falls back to the transcript; empty and invalid stdin are allowed; the legacy numeric lock still counts; the JSON lock counts and preserves the other keys. `test/plugin.mjs`: the `SubagentStop` entry carries the matcher and both entries point at the `.mjs` script; the script is executable. `test/implement.mjs`: `run_start` writes the JSON lock; `status.lockCounter` reads it.
**Out of scope:** the cap semantics (V3-04).
**Verification:** `npm test -- guard implement`; `bash -n`/`node --check` via `npm run lint`.
**Depends on:** none

### V3-04: the guard cap counts stalls, not stops

**Goal:** A 76-task plan cannot exhaust the cap by making normal progress.
**Files touched:** `scripts/implement-guard.mjs`, `mcp/server.mjs` (`taskDone`, `taskBlock`, `runStart`, `status`), `test/guard.mjs`, `test/implement.mjs`, `docs/architecture.md`, `docs/operations.md` (env table, symptom table), `README.md` (The guard hook), `CHANGELOG.md`
**Design constraints:**

- `foundry_task_done`, `foundry_task_block` and `foundry_run_start` reset the lock's `count` to 0 when the lock exists. The counter therefore measures blocked stops since the last task state change.
- Default `FOUNDRY_GUARD_CAP` becomes 60. Keep the env override. Add `guardCap` to `docs/foundry.json` config (default 60) and have `run_start` write the effective cap into the lock JSON (`cap`); the hook uses the lock's `cap` if present, else the env, else 60. This lets the planner raise it per project without touching the launcher's environment.
- When the cap trips, the hook's `systemMessage` names the task that stalled (the first `[~]`), the count, and the recovery: `foundry_task_block` it by hand or resume the flight.
- `foundry_task_done`'s return gains `guardReset: true` so the transcript shows it.

**Acceptance tests:** `test/implement.mjs`: after N blocked stops, `task_done` resets the count to 0; `task_block` resets; `run_start` on resume resets. `test/guard.mjs`: the cap comes from the lock's `cap` when present, else the env, else 60; the trip message names the stalled task.
**Out of scope:** any change to what counts as an open task.
**Verification:** `npm test -- guard implement`.
**Depends on:** V3-03

## Phase B — run hygiene (the run does not damage the repo or the operator)

### V3-05: pre-existing untracked files are invisible to the run

**Goal:** The implementer never has a reason to move, delete or gitignore a file it did not create, and the MCP never deletes one.
**Files touched:** `mcp/server.mjs` (`runStart`, `taskDone`, `taskBlock`, `runFinish`, `status`), `skills/implement/SKILL.md`, `skills/review-build/SKILL.md`, `test/implement.mjs`, `test/drive.mjs`, `docs/mcp-tools.md`, `docs/architecture.md` (State on disk), `CHANGELOG.md`
**Design constraints:**

- `run_start` records every `??` path from `git status --porcelain --untracked-files=all` into state as `preexistingUntracked: [...]` (relative paths, sorted). On `alreadyStarted` resume, keep the recorded list; do not re-record.
- `task_done`'s dirty check and `run_finish`'s clean check ignore lines whose path is in the list (exact path match; directories recorded by `--untracked-files=all` are individual files, so no prefix logic).
- `task_block`'s `git clean -qfd` becomes `git clean -qfd -e <path>` for each recorded path (`-e` takes a pattern; paths with glob characters must be escaped). Add a test that proves an untracked file present before `run_start` survives a `task_block`.
- `foundry_status` exposes `preexistingUntracked`.
- Implement skill: a new short section "Files you did not create": never move, delete, rename or add to `.gitignore` any file that existed before the run; `foundry_task_done` ignores them; if one is in your way, it is not, leave it.
- Review skill: under Boundaries, add that a change to `.gitignore`, `.gitattributes`, editor or CI config not called for by a task is a finding (F-17).
- The dirty-check error text, when it does fire, lists only the offending paths and says "commit them as part of `<id>` or `git checkout --`/`git clean` them", never "tidy".

**Acceptance tests:** `test/implement.mjs`: an untracked file present before `run_start` is recorded; `task_done` succeeds with it still untracked; `task_block` leaves it in place; `run_finish` succeeds with it present; a file created *after* `run_start` still fails `task_done` with the path listed. `test/drive.mjs`: seed an untracked operator file before the flight and assert it survives to the end unchanged.
**Out of scope:** tracked-but-modified files (still a refusal).
**Verification:** `npm test -- implement drive`.
**Depends on:** none

### V3-06: `foundry_agents_sync` sets up the MCP allow rule

**Goal:** The first flight in a project does not stall on a permission prompt for the plugin's own tools.
**Files touched:** `mcp/server.mjs` (`agentsSync`, `configShow`), `test/routing.mjs`, `docs/mcp-tools.md` (`foundry_agents_sync`, `foundry_config_show`), `docs/operations.md` (Running a flight), `README.md` (Per-project use), `CHANGELOG.md`
**Design constraints:**

- After writing agents, ensure `.claude/settings.local.json` in the project contains `permissions.allow` with the entry `mcp__plugin_foundry_foundry`. Read-merge-write: preserve every other key and every other allow entry; create the file if absent; refuse with a clear error (and still return the agents result with `permissions: "failed: <why>"`) if the file exists and is not valid JSON, rather than overwriting it.
- Treat the rule as `present` if it already appears in `.claude/settings.local.json` **or** `.claude/settings.json` (the committed one), so a project that chose the committed file is not nagged. Do not read or write the user's global settings.
- Result field `permissions`: `"added"`, `"present"`, or `"failed: …"`. `foundry_config_show` reports `permissionRule: "present" | "missing"`.
- Claude Code gitignores `.claude/settings.local.json` only when it creates the file itself; a file the sync creates must be excluded by hand, so add `.claude/settings.local.json` to `.git/info/exclude` the same way the agent files are, and report it in the existing `exclude` field.
- Document the exact rule string once, in `docs/operations.md`, and have README and routing.md link to it rather than repeat it.

**Acceptance tests:** `test/routing.mjs`: a fresh repo gets the file with exactly the one allow entry; an existing file with other keys and entries keeps them and gains the entry; a second sync reports `present`; an entry in `.claude/settings.json` alone reports `present` and writes nothing; invalid JSON is not overwritten and is reported.
**Out of scope:** any other permission (Bash, Write) — those are the generated agents' `permissionMode` and V3-13's `tools:`.
**Verification:** `npm test -- routing`.
**Depends on:** none

### V3-07: run policies — signing, push, PR — and `foundry_run_halt`

**Goal:** The operator's decisions about signing, pushing and PRs are recorded once, forwarded to every stage, and a run that cannot honour them stops cleanly without losing work.
**Files touched:** `mcp/server.mjs` (`cfg`, `runStart`, `runFinish`, `next`/`PROMPTS`, `status`, new `runHalt`, `TOOLS`), `skills/implement/SKILL.md`, `skills/go-flight/SKILL.md` (allowed-tools), `test/implement.mjs`, `test/state.mjs`, `test/plugin.mjs`, `docs/mcp-tools.md`, `docs/operations.md` (config table, Halts, symptom table), `docs/architecture.md` (stage machine, state on disk), `README.md` (MCP tools count), `CHANGELOG.md`
**Design constraints:**

- Config gains `policies: { "signing": "auto" | "off" | "required", "push": true | false, "pr": "draft" | "none" }` with defaults `auto`, `true`, `draft`. Validate values; refuse on unknown keys or values with a message naming the legal ones.
- `run_start` records the effective policies in state (`policies`) and returns them. Signing probe, once per `run_start` when not `alreadyStarted`:
  - Determine whether signing is configured: `git config --get commit.gpgsign` is `true`.
  - If configured, prove it works by creating a signed object without touching the branch: `git commit-tree -S HEAD^{tree} -m "foundry signing probe"` with `GIT_TERMINAL_PROMPT=0` and a 30 s timeout via `spawnSync`. A dry run is not enough (F-05). Discard the resulting sha.
  - `required`: probe failure refuses `run_start` with the git error and "fix the signing agent or set policies.signing to off".
  - `off`: set `git config --local commit.gpgsign false`; record `signing: "off"` in state.
  - `auto`: probe success → keep signing, record `"on"`; not configured → record `"none"`; probe failure → set `commit.gpgsign false` locally, record `"off (probe failed: <first line>)"`, and include it in the return so the transcript shows it.
  - Restore nothing at `run_finish`: the local config change is deliberate and visible in `git config --local -l`; document that.
- `run_finish` honours `push: false` (`push: "skipped: policy"`) and `pr: "none"` (`pr: "skipped: policy"`).
- `foundry_next`'s implement, review and summarize prompts gain one sentence: `Run policies: signing=<x>, push=<on|off>, pr=<draft|none>.` The controller forwards them by forwarding the prompt verbatim, which it already does.
- New tool `foundry_run_halt({ reason })`: writes `halted: <reason>` into state, removes the lock, commits state and `PROGRESS.md` if they changed (`chore: run halted`), and returns `{ halted, branch, head, dirty }`. It never resets or cleans the tree. `foundry_next` then returns `halt` with the reason. Clearing `halted` is the existing documented hand edit.
- Implement skill, new section "When a commit cannot be made": if `git commit` fails or hangs on signing, check the policy in the run_start result: `off`/`auto` → run `git config --local commit.gpgsign false`, retry once, log `Signing: disabled mid-run (<error>)` in the task log; `required` → do not bypass; call `foundry_run_halt` with the error and stop. Also list the other legitimate halt reasons: disk full, a verify command that cannot run at all, a base branch that vanished.
- `foundry_status` exposes `policies` and the signing outcome.

**Acceptance tests:** `test/implement.mjs`: defaults resolve; unknown policy values refuse; `signing: off` sets the local config and records it; `signing: required` with `commit.gpgsign true` and no working signer (a bogus `gpg.program` in the temp repo) refuses; `auto` under the same conditions disables and records the probe failure; `push: false` skips the push with a bare remote present; `pr: none` skips PR creation; `run_halt` writes the reason, removes the lock, leaves an uncommitted file alone, and `next` returns `halt`. `test/plugin.mjs`: tool count is thirteen and go-flight allows the new tool.
**Out of scope:** detecting a signer that dies mid-run from inside the MCP (the skill handles it).
**Verification:** `npm test -- implement state plugin`.
**Depends on:** V3-03 (lock format), V3-05 (untracked list survives the halt)

## Phase C — review rounds (the reviewer never guesses)

### V3-09: the MCP owns the review round number

**Goal:** A reviewer never has to pre-increment a round number, and a `REVIEW.md` stamped with the wrong round is refused before it is committed.
**Files touched:** `mcp/server.mjs` (`status`, `next`/`PROMPTS`, `reviewSubmit`), `skills/review-build/SKILL.md`, `test/state.mjs`, `test/review.mjs`, `test/drive.mjs`, `docs/mcp-tools.md`, `docs/architecture.md` (Review rounds), `CHANGELOG.md`
**Design constraints:**

- Define the two numbers once, in `docs/architecture.md`: `round` is the number of review-fix rounds whose tasks have been queued so far (0 during the initial build); `reviewRound` is `round + 1`, the number the next review is stamped with and the prefix of the fix tasks it may queue.
- `foundry_status` and `foundry_next` expose `reviewRound`. The review prompt says "This review is round <reviewRound>; write `Round: <reviewRound>` on the second line of docs/REVIEW.md and use `R<reviewRound>-<nn>` when a fix task's dependsOn must reference another fix task in the same submission."
- `review_submit` reads `REVIEW.md`'s `Round:` line and refuses when it is missing or not equal to `reviewRound`, with a message giving the expected value. Both verdicts.
- The approval commit message becomes `review: round N approved` so `git log --grep '^review:'` lists every round uniformly.
- `review_submit` validates `dependsOn` entries: each must be an existing task id in `PROGRESS.md` or an `R<reviewRound>-<nn>` id within the submission's range; refuse otherwise, naming the bad id.

**Acceptance tests:** `test/state.mjs`: `reviewRound` is `round + 1` at every point in the decision table. `test/review.mjs`: `Round: 1` is accepted in round 0, `Round: 0` and a missing line are refused with the expected value in the message; an approval commit subject is `review: round 1 approved`; a `dependsOn` naming `R1-02` in a two-task submission is accepted, `R1-03` or `R2-01` is refused. `test/drive.mjs` updated for the new commit subject.
**Out of scope:** renumbering anything already on disk from a 0.2 flight.
**Verification:** `npm test -- state review drive`.
**Depends on:** none

### V3-10: converging rounds do not halt the flight

**Goal:** A flight whose review findings are shrinking keeps going; a flight that is not converging still stops for a human.
**Files touched:** `mcp/server.mjs` (`cfg`, `reviewSubmit`, `next`, `status`, `DEFAULT_STATE`), `skills/review-build/SKILL.md`, `skills/summarize/SKILL.md`, `test/review.mjs`, `test/state.mjs`, `docs/operations.md` (Halts, config table), `docs/architecture.md` (Review rounds), `README.md` (Resuming and halting), `CHANGELOG.md`
**Design constraints:**

- State gains `rounds: [{ round, fixTasks, unblocked, verdict, at }]`, appended by `review_submit`, so the history of finding counts is on disk (the summarizer's review-history section reads it instead of reconstructing it from git).
- Config: `maxRounds` (default 3) now bounds **non-converging** rounds; `maxRoundsHard` (default 6) is the absolute ceiling. A round is non-converging when its fix-task count (tasks plus unblocks) is greater than or equal to the previous round's. Round 1 is always allowed.
- `review_submit` halts when the new round number exceeds `maxRoundsHard`, or when the number of non-converging rounds so far exceeds `maxRounds`. The `halted` message says which rule fired, the counts per round, and how to continue.
- `foundry_next`'s existing `open > 0 && round > maxRounds` check is replaced by "halted in state" only; the decision is made once, in `review_submit`, and recorded.
- Review skill: add a `## Notes` section to the `REVIEW.md` format for findings that need no task (readability, naming, low residue); say that an approval may carry notes and that a note is not a finding. Keep the approval bar (categories 1–3 clean, no blocked tasks) unchanged.
- Summarize skill: the review-history section reads `rounds` from `foundry_status` and lists notes carried on approval.

**Acceptance tests:** `test/review.mjs`: sequence 15 → 3 → 2 → 1 fix tasks with `maxRounds: 3` does not halt; 4 → 4 → 4 with `maxRounds: 2` halts on the third with "non-converging" in the message; any sequence halts past `maxRoundsHard`; `state.rounds` records each submission. `test/state.mjs`: `next` returns `halt` only from `halted`.
**Out of scope:** any automatic approval threshold (rejected in Decisions).
**Verification:** `npm test -- review state`.
**Depends on:** V3-09

### V3-12: constraints with fixtures, checked by `foundry_verify`

**Goal:** A `CLAUDE.md` constraint is a rule with proof that its check works, and a grep with a blind spot fails its own fixture instead of passing for three rounds.
**Files touched:** `mcp/server.mjs` (`cfg`, `verify`, new `checkConstraints`), `skills/plan-build/SKILL.md`, `skills/review-build/SKILL.md`, `skills/implement/SKILL.md`, `templates/constraints.example.json` (new), new suite `test/constraints.mjs` + `test/run.mjs` entry, `test/plugin.mjs` (templates are referenced from docs), `docs/operations.md` (config table + a new "Constraints" section), `docs/mcp-tools.md` (`foundry_verify`), `docs/writing-specs.md` (§ Principles a reviewer can check mechanically), `CONTRIBUTING.md` (suite table), `README.md` (Testing), `CHANGELOG.md`
**Design constraints:**

- Config gains `constraints: [ { "id", "description", "paths": ["src/"], "exclude": ["src/config/"], "pattern": "<JS regex source>", "flags": "i", "shouldMatch": ["line", …], "shouldNotMatch": ["line", …] } ]`. Every rule requires `id`, `paths`, `pattern`, at least one `shouldMatch` and at least one `shouldNotMatch`. Refuse anything else with the rule id in the message.
- `foundry_verify` runs constraints first, before the shell commands: (1) self-test each rule against its fixtures; a fixture that disagrees fails the rule with `fixture` in the result (`"shouldNotMatch line 2 matched"`); (2) scan every tracked file under `paths` minus `exclude` (`git ls-files -- <paths>`, so untracked and ignored files are never scanned) line by line; each hit is `{ file, line, text }`. The result gains `constraints: { ok, results: [ { id, ok, fixture, hits } ] }` and the top-level `ok` includes it. `files` from the call does not narrow the scan; constraints are whole-repo, always.
- Line-based only: no multi-line patterns. Say so in the docs; the planner can express multi-line rules as several line rules.
- Plan-build skill: every constraint under `## Constraints` in `CLAUDE.md` that can be expressed as a line pattern must also appear in `constraints`, with fixtures covering each syntactic shape the implementer might use (name the F-14 shapes as the example: `'key' => 5`, `= 5;`, an allow-list). A constraint that cannot be a line pattern says so in `CLAUDE.md` ("reviewer checks by reading").
- Review skill: category 1 runs `foundry_verify` and reads its constraint results; when the reviewer finds a violation by reading that the rule missed, the fix task must add the missed shape to `shouldMatch` (and `foundry.json` to its files) so the blind spot is closed on disk.
- Implement skill: a `foundry_verify` constraint hit is a failing test; fix the code, not the rule, unless the task explicitly changes the rule.
- `templates/constraints.example.json`: three worked rules (a forbidden import, a hard-coded tunable in the three F-14 shapes, a forbidden call outside a module) with fixtures; linked from `docs/operations.md`.

**Acceptance tests:** `test/constraints.mjs` (new): a rule with correct fixtures and no hits passes; a hit is reported with file, line and text; a `shouldNotMatch` line that matches fails the rule with `fixture` set and no scan hits reported for it; `exclude` removes a directory; untracked files are not scanned; missing `shouldMatch` refuses; the example template passes its own self-test. `test/plugin.mjs`: `run.mjs` lists the suite; the template is valid JSON and linked from the docs.
**Out of scope:** AST-aware checks; a shared rule library beyond the three examples.
**Verification:** `npm test -- constraints implement plugin`.
**Depends on:** V3-11 (shares the `cfg()` normalisation)
