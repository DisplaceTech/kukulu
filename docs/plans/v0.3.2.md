# Foundry 0.3.2 — plan

Fix what the first flight on 0.3.1 tripped over. The
`project-b` flight
(`../feedback/2026-09-23-project-b.md`)
logged five friction entries through the new `foundry_feedback_log`
channel. Four of them are defects or gaps in the behavior 0.3.1 already
has:

- the implement guard blocks the flight controller;
- the agent fallback passes a model id the `Agent` tool rejects;
- `foundry_review_submit` returns stale counts;
- auto mode refuses the reviewer's hand-edited mutation tests.

This release fixes those four.

The fifth entry (F-05, parallel workstreams) changes how a flight flows.
It is planned separately in [`v0.4.md`](./v0.4.md) and ships as 0.4.0.

This is a patch release by the same test 0.3.1 used. No stage gains
judgment, no `foundry_next` transition changes, and nothing about rounds,
verdicts or policies moves. One tool is added (`foundry_mutate`), and it
only changes how the reviewer does something it was already told to do.

## Decisions

- **F-01: the guard identifies the implementer by a real tool call, not
  a substring.** `scripts/implement-guard.mjs` decides that a `Stop`
  belongs to the implementer when the session's transcript contains the
  text `foundry_run_start` anywhere. The controller's transcript always
  contains that text, because `foundry_next`'s implement prompt says
  "Call foundry_run_start, then loop…" and the controller passes it on
  verbatim in its `Agent` call. So every controller turn end was blocked,
  and each block used up `guardCap`. The fix parses the transcript as
  JSONL and counts only assistant `tool_use` blocks whose `name` is
  `foundry_run_start` (bare, or with any `mcp__…__` prefix). The same
  test 0.3.0 intended is now made exactly.
- **F-02: `foundry_next` returns the model value the `Agent` tool can
  actually take.** Generated agent files accept a full `claude-*` id in
  `model:`, so routing may keep full ids. The `Agent` tool's `model`
  parameter accepts only `sonnet`/`opus`/`haiku`/`fable`, so the fallback
  path needs the family alias:
  - `foundry_next` gains `agentModel`: the value to pass as `Agent`'s
    `model` when `agentFallback` is true, or `null` when no model should
    be passed (`inherit`).
  - A `claude-*` id whose family it cannot map counts as unreachable,
    exactly like a non-Anthropic model, and gets `restartRequired`.
  - An alias means "latest of that family", which may not be the version
    pinned in routing. So `foundry_next` also returns `agentModelExact`
    (false when the value was mapped down from a full id), and the
    controller prints a one-line note when it is false.
- **F-03: return values are computed after the write.**
  `appendTaskLines` changes `pr.lines` but never `pr.tasks`, so
  `counts(pr.tasks)` in `reviewSubmit` came from the pre-append list. Fix
  it at the return site by re-parsing after `writeProgress`. Also audit
  every other `counts(...)` return for the same pattern.
- **F-04: mutation testing moves into the MCP as `foundry_mutate`.** The
  review skill tells the reviewer to edit source in the tree and restore
  it with `git checkout`. Under auto mode, a reviewer that has been told
  "do not fix code yourself" and then edits source looks like exactly
  what the classifier should refuse. A scratch copy (`git archive`) can't
  run suites tied to the repo root, such as wp-env, so it is no
  substitute. A deterministic tool fixes both problems:
  - It applies one exact find/replace to one tracked, clean file.
  - It runs the verify commands that file would trigger (so wp-env style
    `extraVerify` suites run where they must), always restores the file
    in `finally`, and reports whether the mutation was killed.
  - It commits nothing.
  - The reviewer never holds an Edit on source, and the restore can't be
    forgotten.
  - A crash between mutate and restore is recovered by a sentinel file
    that the next Foundry call notices.

V3.2-01 through V3.2-04 are independent of each other. Do them in order
anyway, one commit each. V3.2-05 comes last.

## V3.2-01: the implement guard matches a real `foundry_run_start` call (F-01)

**Goal:** A go-flight controller waiting on a background implementer is
never blocked by the Stop hook. An implement stage run directly in the
main session still is.

**Files touched:** `scripts/implement-guard.mjs`, `test/guard.mjs`,
`docs/architecture.md` (the unattended-contract paragraph describing the
guard's decision rule), `docs/operations.md` if it describes the rule.

**Design constraints:**

- Replace `transcriptCalledRunStart(path)` with a function that reads
  the file, splits on `\n`, and `JSON.parse`s each non-blank line,
  skipping lines that fail. It returns true only if some entry's
  `message.content` is an array containing an item with
  `type === "tool_use"` and a `name` matching
  `/^(?:mcp__.+__)?foundry_run_start$/`.
- Add an `{ includeSidechain }` option.
  - For `Stop`, ignore entries with `isSidechain === true`. A subagent's
    calls that are logged inline in the parent transcript belong to the
    subagent, not this session.
  - For `SubagentStop` with no `agent_type`, prefer
    `input.agent_transcript_path` when present, otherwise
    `transcript_path`, and include sidechain entries. There, the
    subagent's calls are the point.
- Unreadable file or zero parseable lines means false (allow), as today.
- Update the header comment's rule 3 to say "a `tool_use` of
  `foundry_run_start`", and cite F-01 of the 2026-09-23 feedback file.

**Acceptance tests** (`test/guard.mjs`):

- Replace the `{"tool":"foundry_run_start"}` fixtures with realistic
  transcript lines: an assistant entry whose `message.content` holds a
  `tool_use` named `mcp__plugin_foundry_foundry__foundry_run_start`.
  Existing block/allow expectations must still hold.
- **Regression for F-01.** Build a controller-shaped transcript: a
  `foundry_next` `tool_use`, a `tool_result` whose text contains
  "Call foundry_run_start, then loop on foundry_task_next", and an `Agent`
  `tool_use` whose `input.prompt` contains the same text. A `Stop` with
  that transcript is allowed, and the lock's counter is not incremented.
- A transcript where the `foundry_run_start` `tool_use` sits only in an
  `isSidechain: true` entry: `Stop` allows, and `SubagentStop` without
  `agent_type` blocks.
- The bare name `foundry_run_start` (no prefix) and the
  `mcp__foundry__foundry_run_start` form both count.
- A transcript with one garbage line plus one real `tool_use` line still
  blocks.

**Verification:** `npm test -- guard`.

**Depends on:** none.

## V3.2-02: `foundry_next` returns an `Agent`-legal fallback model (F-02)

**Goal:** When the controller has to fall back to the plugin agent, the
model it passes is one the `Agent` tool accepts. It is never a raw
`claude-*` id.

**Files touched:** `mcp/server.mjs` (a new `agentToolModel(model)` helper
beside `isAnthropicModel`, plus `next()`'s `agentInfo`/`stage`,
`agentsSync`'s `restartRequired`, and the `foundry_next` tool
description), `skills/go-flight/SKILL.md`, `test/state.mjs`,
`test/routing.mjs`, `docs/mcp-tools.md` (`foundry_next` return table),
`docs/routing.md`.

**Design constraints:**

- `agentToolModel(model)` returns `{ value, exact }` or `null`:
  - `sonnet`/`opus`/`haiku`/`fable` → `{ value: model, exact: true }`
  - `inherit` → `{ value: null, exact: true }` (pass no model)
  - `/^claude-(opus|sonnet|haiku|fable)-/` → `{ value: <family>, exact: false }`
  - anything else, including an unrecognised `claude-*` family → `null`
    (unreachable by the Agent tool)
- In `next()`, `restartRequired` under fallback is
  `agentToolModel(model) === null`, replacing `!isAnthropicModel(model)`.
  `agentsSync`'s `restartRequired` uses the same predicate, so the two
  can never disagree.
- Keep `isAnthropicModel` for `effortDropped`. Effort in a generated
  agent file is legal for any Anthropic model, full id or alias.
- Every `stage(...)` result gains `agentModel` (the mapped `value`, or
  `null`) and `agentModelExact`. `model` stays as it is: the routed
  value, for display.
- `go-flight` changes:
  - Step 4 passes `model: agentModel` (omitted when null) only when
    `agentFallback` is true.
  - The "agent type not found" retry also uses `agentModel`.
  - When `agentFallback` is true and `agentModelExact` is false, print
    one line before spawning: `note: <role> routed to <model>; the Agent
    tool only takes aliases, so this stage runs on <agentModel> (latest
    of that family) until the session loads the generated agent.`
  - The step 1 return shape lists the two new fields.
- `docs/routing.md` states the rule. Full ids are fine in routing
  config, and they are exact once the generated agent loads. Only the
  first-population fallback is approximated to the family alias.

**Acceptance tests:**

- `test/state.mjs`: with the reviewer routed to `claude-opus-5-5` and no
  generated agents, `foundry_next` at the review stage returns
  `agentFallback: true`, `agentModel: "opus"`, `agentModelExact: false`,
  `restartRequired: false`, and `model: "claude-opus-5-5"`.
- With a role routed to `sonnet`, the result is `agentModel: "sonnet"`
  and `agentModelExact: true`. With `inherit`, it is `agentModel: null`.
- With a role routed to `claude-mystery-9` (unknown family) under
  fallback, the result is `restartRequired: true`.
- `test/routing.mjs`: `foundry_agents_sync` on a fresh directory with a
  role on `claude-opus-5-5` returns `restartRequired: false`. On
  `claude-mystery-9` it returns `true`. The generated agent file still
  says `model: claude-opus-5-5` verbatim.
- `test/plugin.mjs`: `go-flight`'s SKILL.md mentions `agentModel`, and
  no longer tells the controller to pass `model: model`.

**Verification:** `npm test -- state routing plugin`.

**Depends on:** none.

## V3.2-03: `foundry_review_submit` counts include its own fix tasks (F-03)

**Goal:** Every tool's returned `counts` reflect `PROGRESS.md` as that
same call left it.

**Files touched:** `mcp/server.mjs` (`reviewSubmit`, plus any other
return site the audit finds), `test/review.mjs`.

**Design constraints:**

- In `reviewSubmit`'s `CHANGES REQUESTED` branch, return
  `counts: counts(parseProgress().tasks)`, computed after
  `writeProgress(pr)`.
- Don't patch `appendTaskLines` to fake `pr.tasks` entries. Line indices
  would be wrong for any later edit in the same call, and re-parsing is
  cheap and obviously correct.
- Audit every `counts(pr.tasks)` return (`runStart`, `taskNext`,
  `taskDone`, `taskBlock`, `runFinish`, `status`). For each, confirm no
  line was added or removed between the parse and the return. Mention
  the audit result in the commit body, even if nothing else changed.

**Acceptance tests** (`test/review.mjs`):

- A `CHANGES REQUESTED` submit with three tasks against an all-done
  26-task PROGRESS returns `counts.todo === 3`, `counts.open === 3` and
  `counts.total === 29`.
- A submit carrying one fix task plus one `unblock` of a blocked task
  returns `todo === 2`, `blocked` reduced by one, and `total` increased
  by one.

**Verification:** `npm test -- review`.

**Depends on:** none.

## V3.2-04: `foundry_mutate` — reviewer mutation testing without hand edits (F-04)

**Goal:** The reviewer can prove a test would fail without the mechanic
it covers. This works for root-bound suites like wp-env, without the
reviewer ever editing source and without any chance of leaving a
mutation behind.

**Files touched:** `mcp/server.mjs` (`P.mutation`, `recoverMutation`,
`mutate`, the `TOOLS` entry, calls to `recoverMutation` from `verify`
and `reviewSubmit`), `agents/reviewer.md` (`tools:`),
`skills/review-build/SKILL.md`, `test/review.mjs`, `test/routing.mjs`
(only if the generated-tools assertion needs a fixture update),
`test/plugin.mjs`, `docs/mcp-tools.md` (new section),
`docs/architecture.md` ("Who may write what": the reviewer may now cause
a transient source edit, always through the MCP and always reverted).

**Design constraints:**

- Signature: `foundry_mutate({ file, find, replace, commands? })`. It
  refuses (`ToolError`, worded for a model to recover from) when any of
  the following hold:
  - `.foundry/implement.lock` exists. Mutation testing is a review-stage
    tool, not something to run mid-implement.
  - `file` resolves outside `ROOT`, or is not tracked
    (`git ls-files --error-unmatch`).
  - `file` has uncommitted changes (`git diff --quiet HEAD -- <file>`
    fails).
  - `find` is empty, or appears a number of times other than exactly
    one. The error names the count and asks for more context in `find`.
  - `commands` contains a string that doesn't equal some configured
    `verify` or `extraVerify` `cmd`. The error lists the legal ones.
- Command selection:
  - Default: `cfg().verify`, plus the `extraVerify` entries whose prefix
    `file` falls under. This is exactly what
    `foundry_verify({ files: [file] })` would run. Share that selection
    code rather than duplicating it.
  - When `commands` is given, run only those, keeping each one's own
    configured `timeoutMs`.
  - Constraints are not run.
- Sequence:
  1. `recoverMutation()`.
  2. Write `.foundry/mutation.json` as
     `{ file, at, original: <sha of the blob at HEAD> }`.
  3. Write the mutated content, then run the commands.
  4. In `finally`: `git checkout -- <file>` and delete the sentinel.
  5. Confirm `git diff --quiet HEAD -- <file>`. If the restore did not
     take, throw a `ToolError` that says so plainly and names the file.
     Also auto-log feedback (`stage: "review"`,
     `category: "mutation-restore"`) under the usual
     `policies.feedback` guard, without committing. The next commit the
     reviewer makes carries it, same as 0.3.1's internal auto-log points.
- `.foundry/mutation.json` is excluded per clone through
  `gitPath("info/exclude")`, the same way `agentsSync` excludes agent
  files. Never write it to `.gitignore`: that would dirty the reviewed
  branch.
- `recoverMutation()`: if the sentinel exists, `git checkout --` its
  `file`, delete the sentinel, and return the restored path, otherwise
  `null`. Call it at the top of `mutate`, `verify` and `reviewSubmit`,
  and surface a non-null result in each tool's return as
  `recoveredMutation`. Being loud is right: something crashed mid-mutate.
- Return
  `{ file, killed, results, recoveredMutation }`, where `killed` means
  at least one command failed (the tests noticed). Also add a one-line
  `verdict`: `"killed: the tests caught the mutation"` or
  `"survived: no command failed — the mechanic is untested"`.
- Tool description, in the style of the others: applies one exact
  find/replace to one clean tracked file, runs the verify commands that
  file triggers, always restores the file, and commits nothing. It is
  for reviewers checking that a test fails without the mechanic.
- `agents/reviewer.md` `tools:` gains
  `mcp__plugin_foundry_foundry__foundry_mutate`.
- `skills/review-build/SKILL.md` replaces "Sample at least one test per
  module by deleting or inverting the mechanic … `git checkout --
  <file>`" with this: sample at least one test per module by calling
  `foundry_mutate` with a `find`/`replace` that deletes or inverts the
  mechanic. Expect `killed`. A `survived` result is a category-3
  finding. Never edit source in the working tree yourself, not even
  temporarily: the tool restores the file, and you cannot guarantee
  that you will.
- The tool count becomes fifteen. Update the `test/plugin.mjs` assertion
  and the go-flight or reviewer tool lists here. Leave the prose counts
  in `docs/mcp-tools.md` and `README.md` for V3.2-05, but add the new
  tool's own section now.

**Acceptance tests** (`test/review.mjs`, using a fixture project whose
verify command runs a real test against a source file):

- Mutating the tested line gives `killed: true`. Afterwards the file is
  byte-identical to HEAD, `git status --porcelain` is empty, no commit
  was made, and there is no sentinel.
- Mutating a line no test covers gives `killed: false`, and the file is
  restored.
- A verify command that times out still restores the file.
- Each of these refuses, and leaves the file untouched:
  - `find` matching zero or two times;
  - an untracked file;
  - a file with a pre-existing uncommitted edit (which must survive
    exactly as it was);
  - a path outside the repo;
  - an unknown entry in `commands`;
  - a present implement lock.
- `extraVerify` selection: with
  `extraVerify: { "src/special/": ["<cmd that fails>"] }`, mutating a
  file under `src/special/` runs that command and mutating elsewhere
  does not.
- Crash recovery: hand-write a sentinel and a mutated file, then call
  `foundry_verify`. The file is restored, the sentinel is gone, and
  `recoveredMutation` names the file.
- `test/plugin.mjs`:
  - `agents/reviewer.md` lists the tool;
  - `review-build` mentions `foundry_mutate` and no longer contains
    `git checkout -- <file>`;
  - the server defines fifteen tools.

**Verification:** `npm test -- review plugin routing`.

**Depends on:** none.
