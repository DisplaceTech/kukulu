# Foundry 0.3.1 — plan

Automate the feedback route. Today, "pipeline friction" only reaches
`docs/SUMMARY.md` if a flight gets all the way to an `APPROVED` review and
the summarizer runs — and even then it depends on the implementer and
reviewer having remembered to write a `## Pipeline friction` heading into
`HANDOFF.md`/`REVIEW.md`, which the summarizer then has to notice and
transcribe. A flight that halts, blocks, or gets abandoned partway through
— exactly the flights most worth learning from — leaves nothing behind.

This release makes friction capture a first-class, durable, MCP-owned
mechanism (`foundry_feedback_log`, `.foundry/feedback.jsonl`) that works
regardless of how the flight ends, and adds a second half: a way to bring a
downstream project's accumulated feedback back into *this* repo's
`docs/feedback/` for the next compound-engineering pass, without hand
transcription.

This is not a change to what the pipeline decides or how a flight
flows — no stage gains new judgment, no `foundry_next` transition changes,
nothing about `round`/`maxRounds`/verdicts moves. It is a parallel
bookkeeping channel, which is why it ships as a patch release, 0.3.1.

## How to work this plan

- Branch: `release/0.3.1` off `main`. One commit per task, titled
  `<ID>: <title>`. Same conventions as `v0.3.md`: `npm run check` before
  every commit, `pre-commit run --all-files` before the PR, tests live
  with the suite that owns the behavior (a new `feedback` suite for the
  genuinely new surface), documentation lands in the same commit as the
  behavior it describes.
- Read `docs/architecture.md`, `docs/mcp-tools.md` and
  `docs/feedback/README.md` before starting; this plan assumes the reader
  knows the shape of `.foundry/state.json`, `gitCommitIfChanged`, and the
  existing four-stage skill set.
- Do not touch the round/convergence/policy logic from 0.3.0. If a task
  here seems to need to, stop and flag it rather than drifting into a
  second unplanned release.

## Decisions

- **Storage: `.foundry/feedback.jsonl`, one JSON object per line, tracked
  and committed** — the same treatment `.foundry/state.json` already gets,
  for the same reason: it has to survive on the branch/PR after the local
  checkout is gone, which is the whole point of "pull it back here."
  `.foundry/implement.lock` is the one exception in this directory that
  stays gitignored, because it is a lock, not a record.
- **Entry shape:**
  `{ "at": "<ISO 8601>", "stage": "plan"|"implement"|"review"|"summarize"|"controller", "round": <int>, "category": "<short free string>", "message": "<one or two sentences>", "source": "agent"|"auto" }`.
  `stage` and `message` are required; `category` defaults to `"other"`;
  `round` is filled from `state.round`, never supplied by the caller;
  `source` is `"auto"` for entries the MCP writes itself and `"agent"` for
  entries written through the tool. `category` is a free string, not an
  enum — the point of this data is to be read by a human or a model
  writing the next `docs/feedback/*.md` file, and boxing it into a fixed
  vocabulary would lose exactly the specificity that makes an item worth
  reading.
- **`foundry_feedback_log` commits immediately, every call**, as
  `chore: pipeline friction (<stage>)`. This is simpler and more robust
  than trying to make the entry "ride along" with whatever the calling
  agent commits next: it works identically whether the caller is a stage
  agent mid-task, the reviewer, the summarizer, or the flight controller
  before any build branch exists, and it means `.foundry/feedback.jsonl`
  is never a *pending* uncommitted change by the time `foundry_task_done`
  or `foundry_run_finish` run their dirty-tree checks — so **no change is
  needed to those checks at all**. Friction should be rare by nature (it
  flags exceptional events, not routine ones), so one small commit per
  entry is the right amount of noise, not too much.
- **Internal auto-logging does not create a second commit.** Where the MCP
  already commits something at the moment it wants to log friction
  automatically (`foundry_run_halt`, a round-cap halt in
  `foundry_review_submit`, a signing auto-fallback in `foundry_run_start`),
  the entry is appended to `.foundry/feedback.jsonl` and folded into that
  *same* `gitCommitIfChanged` call by adding the feedback path to its file
  list, not logged through the externally-callable tool. Two internal
  helpers: `appendFeedback(stage, message, category)` (write only, no
  commit — used internally) and the `foundry_feedback_log` tool itself
  (write, then commit — used by agents, which have no other commit of
  their own happening at that instant).
- **What auto-logs itself, and what doesn't.** `foundry_run_halt`,
  `foundry_review_submit`'s round-cap halt, and `foundry_run_start`'s
  signing auto-fallback all happen strictly after `foundry_run_start` on
  an active build branch, so an automatic commit there is always exactly
  where you'd expect one. A `foundry_agents_sync` permission-rule failure
  and a `RESTART REQUIRED` stop happen *before* any build branch
  necessarily exists — sometimes on `main` itself, before a flight has
  done anything — so those are **not** auto-logged inside the MCP. Instead
  the flight controller (`go-flight`), which already prints these
  messages, calls `foundry_feedback_log` itself when it does. This keeps
  every MCP-internal auto-commit confined to branches a flight already
  owns, and accepts, as a documented tradeoff, that a controller-logged
  entry before the first `foundry_run_start` lands on whatever branch is
  currently checked out.
- **The `## Pipeline friction` heading convention in `HANDOFF.md` /
  `REVIEW.md` is retired, not kept alongside the new mechanism.** Keeping
  both would mean two places to look and two ways to miss something. Every
  place that told a stage to write that heading now tells it to call
  `foundry_feedback_log` instead, at the moment the friction happens, not
  saved up for end-of-stage prose.
- **An opt-out, because this writes to someone else's repo.**
  `docs/foundry.json` gains `policies.feedback` (boolean, default `true`).
  `false` makes `foundry_feedback_log` and every internal auto-log call a
  documented no-op (`{ logged: false, reason: "disabled by policy" }`,
  never a refusal — a model that calls it should never have to branch on
  whether logging is allowed). This is the same shape as `policies.push`:
  an operator-level toggle, not a pipeline decision.
- **Pulling it back is a skill, not a new MCP tool.** The transformation
  (read a JSONL file, number the new entries, write prose paragraphs
  following the existing `docs/feedback/README.md` convention) is
  mechanical in its bookkeeping and needs judgment in its prose — exactly
  the split Foundry already draws between the MCP and the skills, except
  here the "mechanics" (parsing a few dozen JSON lines, checking for
  duplicates) are simple enough that a model can do them directly with
  `Read`/`Bash`/`Write` without new deterministic tooling. This also keeps
  the change scoped to a maintainer utility rather than growing the
  permanent MCP surface every downstream project's session loads.
- **Pulling is additive and idempotent, never destructive on the source.**
  The pull skill never deletes, truncates, or moves the source project's
  `.foundry/feedback.jsonl` — that would repeat exactly the mistake F-09
  and F-17 fixed, aimed at a different repo instead of the one being
  built. Re-running a pull against the same source is safe: an entry is
  skipped if its exact `at` timestamp already appears in any existing
  `docs/feedback/*.md` file, so only genuinely new entries get numbered
  and added.

## Order of work

V3.1-01 → V3.1-02 → V3.1-03, in that order (each depends on the storage
shape and the commit behavior the previous task establishes). V3.1-04
depends only on V3.1-01 (the entry shape) and can be built in parallel with

everything else.

## V3.1-01: `foundry_feedback_log` and `.foundry/feedback.jsonl`

**Goal:** The storage format, the write path, and the externally-callable
tool exist, independent of anything calling it yet.

**Files touched:** `mcp/server.mjs` (`P` paths, `cfg()`/`validatePolicies`,
`appendFeedback`, `countFeedback`, `feedbackLog`, `status()`, `TOOLS`),
new suite `test/feedback.mjs` + `test/run.mjs` entry, `docs/mcp-tools.md`
(new `foundry_feedback_log` section, `foundry_status` return table).

**Design constraints:**

- `P.feedback = path.join(ROOT, ".foundry", "feedback.jsonl")`.
- `validatePolicies` gains `feedback` (boolean) alongside `signing`/`push`/
  `pr`; `cfg().policies.feedback` defaults to `true`.
- `appendFeedback(stage, message, category, source)`: validates `stage` is
  one of `plan`/`implement`/`review`/`summarize`/`controller` and
  `message` is a non-empty string (throw `ToolError` naming the legal
  stages otherwise — this function is also called internally, so its own
  callers must already pass a valid stage; the validation exists for the
  externally-callable tool's sake and costs nothing to share). Reads
  `state.round` for the `round` field, creates `.foundry/` if it does not
  exist yet, and appends one line of `JSON.stringify(entry)` plus a
  newline to `P.feedback`. Returns nothing; callers commit (or don't)
  themselves.
- `countFeedback()`: reads `P.feedback` if it exists, splits on `\n`,
  filters blank lines, and counts lines that parse as JSON — a line that
  doesn't parse (a partial write from an interrupted process) is skipped,
  not fatal, the same tolerance `loadState()` already gives a corrupt
  `state.json`. Returns `0` if the file does not exist.
- `feedbackLog({ stage, message, category })`: if `policies.feedback` is
  `false`, return `{ logged: false, reason: "disabled by policy" }`
  without touching the filesystem. Otherwise call `appendFeedback` with
  `source: "agent"`, commit `P.feedback` alone as
  `chore: pipeline friction (<stage>)`, and return
  `{ logged: true, count: countFeedback(), commit }`.
- Register the tool:
  `{ name: "foundry_feedback_log", description: "Record one pipeline-friction entry — something Foundry's own tooling cost time on, not the project it is building. Appends to .foundry/feedback.jsonl and commits it immediately, so it survives even if the flight never reaches summarize. Call it the moment friction happens.", inputSchema: S({ stage: { type: "string", enum: [...] }, message: { type: "string" }, category: { type: "string" } }, ["stage", "message"]), fn: feedbackLog }`.
- `foundry_status` gains `feedbackCount` (via `countFeedback()`) so a human
  watching a transcript can see it accumulate without opening the file.
- The tool count is now fourteen; do not update the plugin-suite assertion
  or any doc yet — V3.1-05 does the full documentation and count pass in
  one place so it isn't half-right in the middle of the branch. (Exception:
  `docs/mcp-tools.md` gets its new tool section now, in the same commit as
  the code, per the usual rule that behavior and its doc land together —
  just don't touch the tool-count sentence at the top of that file yet.)

**Acceptance tests** (`test/feedback.mjs`, new suite):

- Calling `foundry_feedback_log` with a fresh project creates
  `.foundry/feedback.jsonl`, containing one line that parses as JSON with
  the right `stage`/`message`/`category`/`round`/`source: "agent"` fields
  and an `at` that parses as a valid ISO date.
- The call also produces a commit whose subject is
  `chore: pipeline friction (implement)` (or whichever stage), touching
  only `.foundry/feedback.jsonl`.
- A second call appends a second line rather than overwriting the first,
  and produces a second, separate commit.
- `category` defaults to `"other"` when omitted.
- `stage` outside the five legal values refuses, naming them.
- Missing or empty `message` refuses.
- `foundry_status`'s `feedbackCount` is `0` before any entry, `1` after
  one, `2` after two.
- A `.foundry/feedback.jsonl` with one valid line and one line of garbage
  (`{not json`) is read by `countFeedback()`/`foundry_status` as count
  `1`, not a thrown error.
- `docs/foundry.json`'s `policies.feedback: false` makes
  `foundry_feedback_log` return `{ logged: false, reason: "disabled by policy" }`,
  creates no file, and commits nothing.
- An invalid `policies.feedback` value (not a boolean) refuses the same
  way an invalid `policies.push` already does.

**Out of scope:** anything calling this tool automatically (V3.1-02),
anything calling it from a skill (V3.1-03).

**Verification:** `npm test -- feedback`.

**Depends on:** none.

## V3.1-02: auto-logging at the MCP's own halt and fallback points

**Goal:** The three places the MCP already decides "something is wrong
enough to stop or degrade" record why, without needing a model to notice
and log it separately.

**Files touched:** `mcp/server.mjs` (`runHalt`, `reviewSubmit`, `probeSigning`/
`runStart`), `test/implement.mjs`, `test/review.mjs`.

**Design constraints:**

- `runHalt({ reason })`: call `appendFeedback("controller", \`Run halted: ${reason}\`, "halt", "auto")`
  before its existing `gitCommitIfChanged([P.state, P.progress], "chore: run halted")`
  call, and add `P.feedback` to that call's file list. Respect
  `policies.feedback` the same way `feedbackLog` does, by wrapping the
  `appendFeedback` call in the same policy check. Duplicate that one-line
  guard here rather than routing through the tool's own function — the
  tool commits on every call, and this call site must not.
- `reviewSubmit`'s `CHANGES REQUESTED` branch: at the point it sets
  `st.halted` (both the `maxRoundsHard` and the non-converging-past-
  `maxRounds` cases), also call
  `appendFeedback("review", st.halted, "round-cap", "auto")` (same
  `policies.feedback` guard), and add `P.feedback` to the existing
  `gitCommitIfChanged([P.review, P.plan, P.progress, P.state], ...)` call
  for that round.
- `probeSigning`'s `auto` fallback path (the branch that disables signing
  after a failed probe and returns `"off (probe failed: ...)"`): the
  caller, `runStart`, is where the git repo and commit context actually
  live, so have `probeSigning` return its outcome as it already does, and
  have `runStart` call `appendFeedback("implement", \`Signing disabled for this run: ${signing}\`, "signing", "auto")`
  when the returned outcome starts with `"off (probe failed"` — guarded by
  `policies.feedback` — and add `P.feedback` to `runStart`'s existing
  `gitCommitIfChanged([P.gitignore, P.progress, P.state], ...)` call. Do
  **not** log anything for the plain `"off"` (explicitly requested) or
  `"none"` (not configured) outcomes — those are not friction, they are
  the operator's or the project's own choice working as intended.
- None of these three call sites use `foundry_feedback_log` (the tool);
  they call `appendFeedback` directly, exactly as designed in the
  Decisions section, so no extra commit appears.

**Acceptance tests:**

- `test/implement.mjs`: `foundry_run_halt` with `policies.feedback` at its
  default produces exactly one commit (not two) whose changed paths
  include both `.foundry/state.json`/`docs/PROGRESS.md` *and*
  `.foundry/feedback.jsonl`; the feedback line's `message` contains the
  halt reason verbatim and `source` is `"auto"`. With
  `policies.feedback: false`, the same call produces its usual commit with
  no feedback file created at all.
- `test/implement.mjs`: a `run_start` whose signing policy is `auto` and
  whose probe fails (the existing broken-`gpg.program` fixture from
  0.3.0's signing tests) produces a feedback entry with `category:
  "signing"` in the same commit as the run-start stamp; a `run_start` with
  `signing: "off"` explicitly, or with signing not configured at all
  (`"none"`), produces no feedback entry.
- `test/review.mjs`: extend the existing non-converging and hard-cap
  convergence tests (from 0.3.0's `driveRounds` helper) to also assert a
  feedback entry with `category: "round-cap"` appears in the same commit
  as that round's `review:` commit, and that a round which does *not*
  halt produces no feedback entry.

**Out of scope:** the flight controller's own logging for `RESTART
REQUIRED` and a failed permission sync (V3.1-03 — those are not MCP-internal
because they can happen before a build branch exists).

**Verification:** `npm test -- implement review feedback`.

**Depends on:** V3.1-01.

## V3.1-03: stage agents log friction directly; the old heading convention is retired

**Goal:** Every stage skill's existing "write a `## Pipeline friction`
heading and hope the summarizer reads it" instruction is replaced with
"call the tool, now" — so friction survives a flight that never reaches
summarize, which is exactly the flight most likely to have some.

**Files touched:** `agents/*.md`, `skills/go-flight/SKILL.md`,
`skills/implement/SKILL.md`, `skills/plan-build/SKILL.md`,
`skills/review-build/SKILL.md`, `skills/summarize/SKILL.md`,
`mcp/server.mjs` (`agentsSync` return / go-flight's failure branch is
prose-only, no server change expected — confirm while doing this task, and
say so in the commit if a server change turns out to be needed),
`test/plugin.mjs`, `test/routing.mjs`.

**Design constraints:**

- Add `mcp__plugin_foundry_foundry__foundry_feedback_log` to all four
  plugin agents' `tools:` lines (`agents/planner.md`, `agents/implementer.md`,
  `agents/reviewer.md`, `agents/summarizer.md`) — every stage may hit
  friction, not only the ones that already call `foundry_run_halt`.
  `renderAgentFile` already copies `tools:` verbatim; no server change
  needed for the generated files to pick this up.
- Add both prefixed forms of `foundry_feedback_log` to `go-flight`'s
  `allowed-tools`, alongside the existing `foundry_run_halt` entry.
- `skills/implement/SKILL.md`: remove the "A `## Pipeline friction`
  section" bullet from the `Finishing` step's `docs/HANDOFF.md` list.
  Add, near the existing "When a commit cannot be made" section (or as its
  own short section), an instruction: the moment something costs time that
  is Foundry's fault and not the project's — a tool refused, a prompt was
  ambiguous, a stall needed a workaround — call `foundry_feedback_log`
  with `stage: "implement"` right then, not saved up for the end.
- `skills/review-build/SKILL.md`: remove the `## Pipeline friction`
  bullet from the `Output` list (`docs/REVIEW.md` no longer carries this
  section). Add the same "call it the moment it happens" instruction with
  `stage: "review"`.
- `skills/plan-build/SKILL.md`: it never had a `## Pipeline friction`
  section (planning rarely hits mid-run friction, but a genuinely
  ambiguous or broken planning experience is still worth recording); add
  one short sentence: if something about *writing* the plan was needlessly
  hard because of Foundry itself, call `foundry_feedback_log` with
  `stage: "plan"`.
- `skills/summarize/SKILL.md`: replace section 8's "Collect it from every
  `## Pipeline friction` heading in `HANDOFF.md` and each round's
  `REVIEW.md`" instruction with: call `foundry_status` for `feedbackCount`;
  if it is greater than zero, read `.foundry/feedback.jsonl` directly
  (`cat` it — it is small, plain JSONL) and render one line per entry:
  stage, category, and the message, in the order logged. If
  `feedbackCount` is `0`, write "None". Keep the "notes-only approval"
  sentence about `## Notes` in `REVIEW.md` — that convention is unrelated
  and stays exactly as it is.
- `skills/go-flight/SKILL.md`: in the "Before the loop" section, when
  `foundry_agents_sync`'s `permissions` field starts with `"failed:"`,
  call `foundry_feedback_log` with `stage: "controller"`, `category:
  "permission-sync"`, and the failure message, *before* printing the
  error and stopping (logging first means the entry survives even though
  the flight is about to end). In the `RESTART REQUIRED` branches (both
  the pre-loop one and the mid-flight `Agent`-call-failed one), call
  `foundry_feedback_log` with `stage: "controller"`, `category: "restart"`,
  and a one-sentence description of which case fired, *before* printing
  the `FOUNDRY: RESTART REQUIRED` line and stopping.

**Acceptance tests:**

- `test/plugin.mjs`: every agent's `tools:` list includes
  `mcp__plugin_foundry_foundry__foundry_feedback_log`; go-flight's
  `allowed-tools` includes both prefixed forms of it; neither
  `skills/implement/SKILL.md` nor `skills/review-build/SKILL.md` contains
  the string `## Pipeline friction` any more (assert its absence, mirroring
  how 0.3.0 asserted the *presence* of the heredoc-fallback sentence); the
  summarize skill's friction section mentions `feedbackCount` and
  `.foundry/feedback.jsonl` rather than scanning headings; the plan-build
  skill mentions `foundry_feedback_log`.
- `test/routing.mjs`: a generated `foundry-<role>` agent's `tools:` field
  matches the plugin agent's exactly (this already exists as a general
  assertion from 0.3.0 — it should pass unchanged once the plugin agents
  carry the new tool, proving the copy-through needs no server change).

**Out of scope:** the pull-back skill (V3.1-04); any change to what
`foundry_run_halt` or `foundry_review_submit` themselves do (V3.1-02
already finished that).

**Verification:** `npm test -- plugin routing`; read each edited skill
file top to bottom once, as the stage agent would, and confirm nothing
still points at the retired heading convention.

**Depends on:** V3.1-01, V3.1-02.

## V3.1-04: `/foundry:pull-feedback` — bring a project's log back here

**Goal:** A maintainer who ran a flight in some other project can turn its
`.foundry/feedback.jsonl` into a new, properly numbered file under this
repo's `docs/feedback/`, without hand-transcribing anything, and without
touching the other project at all.

**Files touched:** new `skills/pull-feedback/SKILL.md`,
`docs/feedback/README.md`, `test/plugin.mjs`.

**Design constraints:**

- This is a standalone utility skill, not a pipeline stage: it has no
  `foundry-<role>` generated agent, is not part of the four-stage loop,
  and is model-invocable by name (no `disable-model-invocation`) the same
  way `go-flight` now is. It runs on whatever model the invoking session
  is already using — it does not need its own pinned model, so it carries
  no `model:`/`effort:` frontmatter of its own (matching the `model:
  inherit` stage skills' pattern, though this one is invoked directly
  rather than through a generated agent).
- Frontmatter: `name: pull-feedback`, a description explaining it reads
  another project's Foundry feedback log and writes a new file under
  `docs/feedback/`. `allowed-tools` is not required to be restrictive here
  (this is a maintainer tool run interactively, not an unattended stage),
  but list `Read, Write, Bash, Glob` explicitly rather than leaving it
  unstated.
- Input: a path to the other project's checkout, taken from the user's
  message or the skill's own arguments. If no path is given, ask for one —
  this is the one skill in the plugin where asking a clarifying question
  is appropriate, since it is always run interactively by a human, never
  by an unattended stage.
- Steps the skill's prose must specify precisely, because they are exactly
  the kind of mechanical step a model does reliably when told plainly and
  unreliably when left to infer:
  1. Read `<path>/.foundry/feedback.jsonl`. If it does not exist or is
     empty, say so and stop — there is nothing to pull.
  2. Parse every line as JSON, skipping (and mentioning) any line that
     doesn't parse.
  3. Determine the project name from the path's basename (or ask, if
     it's ambiguous, e.g. the path is `.` or ends in a generic name) and
     today's date for the destination filename:
     `docs/feedback/<YYYY-MM-DD>-<project>.md`.
  4. Before adding anything, check every existing file in
     `docs/feedback/*.md` for each entry's exact `at` timestamp string; an
     entry whose timestamp already appears anywhere is a duplicate from an
     earlier pull and must be skipped, silently, not re-numbered.
  5. For the entries that remain, assign `F-<nn>` in chronological order
     (by `at`), continuing the numbering already used in the destination
     file if it exists (e.g. a second pull the same day appends `F-04`
     onward rather than restarting at `F-01`), starting at `F-01` for a
     brand-new file.
  6. Render each as a `## F-<nn> — <short title derived from the entry>`
     section: one short paragraph using the entry's `stage`, `category`,
     `round` and `message` — auto-logged entries already read as full
     sentences (they reuse the same text the pipeline itself surfaced) and
     need little more than a heading; agent-logged entries are already
     prose the agent wrote for exactly this purpose. Do not invent detail
     the entry doesn't contain.
  7. Write or append the file with the header shape
     `docs/feedback/README.md` already documents (plugin version — read it
     from the *other* project's installed plugin if determinable, else
     say "version not determined" rather than guessing — and no "addressed
     in" line, since no plan addresses it yet).
  8. Commit the new/updated file in *this* repo as
     `docs: pull feedback from <project>`. Never write to, delete, or
     modify anything under `<path>` — that project is not this run's to
     touch (the same rule F-09/F-17 already established for a flight's own
     untracked files, applied here to an entire other repository).
  9. Report how many new entries were added and how many were skipped as
     duplicates.
- Update `docs/feedback/README.md`: document that `.foundry/feedback.jsonl`
  (JSONL, one entry per line, the shape from V3.1-01) is the source this
  skill reads, name the skill (`/foundry:pull-feedback`), and state the
  dedupe-by-timestamp rule so a future reader understands why re-running a
  pull is safe.

**Acceptance tests:**

- `test/plugin.mjs`: `pull-feedback` is a recognized skill directory with
  a `SKILL.md` carrying frontmatter (extend the existing skill-listing
  assertions — note it is *not* one of the four pipeline stage skills, so
  it does not belong in the `disable-model-invocation`/`model: inherit`
  either/or check that loop already runs; give it its own, smaller
  assertion instead: has frontmatter, has a name matching its directory,
  has a real description, carries no `disable-model-invocation: true`).
  `docs/feedback/README.md` mentions both `foundry_feedback_log` and
  `/foundry:pull-feedback`.

**Out of scope:** any automated / scheduled pulling; any change to how
`foundry_feedback_log` writes its file (V3.1-01 already finished that).

**Verification:** `npm test -- plugin`. Also do one real, manual pull by
hand against a throwaway `.foundry/feedback.jsonl` fixture in a scratch
directory (not part of the test suite — a skill's own prose can't be unit
tested the way a tool can) and confirm the output file reads sensibly; say
so in the commit body.

**Depends on:** V3.1-01 (the entry shape must be final before writing
prose that describes it).

## V3.1-05: documentation, version, release 0.3.1

**Goal:** Every doc reflects fourteen tools and the new file, and the
release is tagged.

**Files touched:** `docs/mcp-tools.md` (tool count sentence at the top),
`docs/architecture.md` ("State on disk" table gains
`.foundry/feedback.jsonl`; "Who may write what" diagram — decide while
doing this whether `foundry_feedback_log`'s writer belongs in it, since
every stage can now write this one file, unlike every other row which has
exactly one writer; if it doesn't fit the diagram's shape, say so in prose
underneath it instead of forcing it in), `docs/operations.md` (config
table gains `policies.feedback`), `README.md` (MCP tools table gains the
row, tool count in prose, `docs/feedback/README.md`'s new content
summarized if the existing bullet undersells it), `CONTRIBUTING.md` (suite
table gains `feedback`, suite-count prose), `package.json`,
`.claude-plugin/plugin.json`, `mcp/server.mjs` (`VERSION`), `CHANGELOG.md`.

**Design constraints:**

- Bump all three version strings to `0.3.1` in lockstep, as the `plugin`
  suite already requires.
- `CHANGELOG.md`: new `## [0.3.1] — <date>` section. Lead with the framing
  from this plan's own opening: this is bookkeeping, not a pipeline
  behavior change — no stage gained judgment, no transition changed.
  Then: `foundry_feedback_log` and `.foundry/feedback.jsonl`; the three
  MCP-internal auto-log points; every stage skill logging directly instead
  of writing a heading only the summarizer read; the new
  `policies.feedback` opt-out; the retired `## Pipeline friction` heading
  convention (call out explicitly that this is a behavior removal from
  0.3.0, so nobody goes looking for a heading that no longer gets
  written); the new `pull-feedback` skill. Fourteen tools now.
- Do not tag. The owner tags after merge, exactly as `v0.3.md` specified
  for 0.3.0.
- Open the PR as a draft with `gh pr create --draft`, title
  `Release 0.3.1`, body: a short summary in the same voice as this plan's
  opening, a plain task list (there is no feedback-item map this time —
  this release wasn't driven by a `docs/feedback/*.md` file, it's the
  thing that will make the *next* one easier to write), a "Deviations"
  section (empty if none), and the `npm test` summary block pasted in.

**Acceptance tests:** `npm run check` clean; `pre-commit run --all-files`
clean.

**Verification:** CI green on the PR (all three workflows).

**Depends on:** V3.1-01 through V3.1-04.

## Definition of done

- `foundry_feedback_log` exists, is documented, and is used by all four
  stage skills and the controller; the old heading convention is gone from
  every skill, not just described as gone.
- A flight that halts partway through (round cap, `foundry_run_halt`, a
  restart) leaves a non-empty `.foundry/feedback.jsonl` behind without any
  human intervention.
- `/foundry:pull-feedback` turns that file into a new, correctly numbered
  `docs/feedback/*.md` file here, and running it twice against the same
  source does not duplicate anything.
- Fourteen tools, everywhere that number is stated.
- `npm run check` and `pre-commit run --all-files` are clean at the tip.
- The PR is a draft, for the owner's review. Nothing is merged or tagged.
